# 架构与边界

## 一期架构
- 后端：Gateway、Auth、Core、IoT 四服务
- 前端：Vue 管理端，承载业务页面、地图、看板、AI 助手界面
- 一期中间件：PostgreSQL、Redis、Mosquitto（MQTT）
- 二期候选中间件：RabbitMQ、MinIO、pgvector

## 服务边界
- Auth：登录、用户、角色、功能权限、菜单、租户上下文、Token 签发与后台管理（后台管理接口统一采用 `/api/auth/admin/**` 路由）
- Core：采购、销售、库存、制造、质量、追溯、统计、AI 工具只读查询
- IoT：设备与凭证管理、MQTT 接入、遥测、状态、告警事实及 IoT 业务操作
- Gateway：统一入口、路由、Token 基础校验、粗粒度过滤和异常包装

Core 物理上保持单服务，内部固定为 `purchasing`、`sales`、`inventory`、`manufacturing`、`quality`、`traceability`、`dashboard`、`ai` 逻辑模块。跨模块只能调用应用服务，禁止直接修改其他模块数据。

Gateway、Auth、Core、IoT 是四个独立后端进程，各自占用一个服务端口。`security-common` 是供 Gateway、Core、IoT 复用的安全基础代码，不是独立进程，不占用端口；在当前工程结构中优先作为 `platform-shared` 内的逻辑安全组件落地，是否单独拆成 Maven 模块后续再决定。

IoT 管控请求不需要先转发给 Core。用户请求经 Gateway 路由到 IoT 后，IoT 使用与 Core 相同的安全上下文和方法级授权规则完成校验；Core 也不作为其他服务的统一业务分发中心。

## 认证与授权边界

一期认证授权采用 OAuth 2.0 / OpenID Connect 语义与 Spring Security 体系，基于 JWT、Redis 会话缓存与 PostgreSQL 事实源落地。

### 请求处理顺序

```text
Frontend
   ↓
Gateway：路由、JWT 签名/有效期/当前会话基础校验、粗粒度过滤
   ↓
Auth / Core / IoT：Spring Security 方法级功能授权
   ↓
业务模块：当前租户、对象状态、数据范围和具体业务规则校验
```

- Gateway 不需要拥有 Core 或 IoT 中的业务方法。它依据请求路径、HTTP 方法和权限元数据进行粗粒度放行，不执行领域业务逻辑。
- Auth 管理用户、角色和功能权限，是功能授权的事实来源；各服务在本服务边界再次执行 `@PreAuthorize` 等方法级授权。
- Core、IoT 的业务模块负责数据权限、状态约束和业务条件。前端隐藏按钮和 Gateway 放行都不能替代业务服务最终校验。
- `security-common` 统一解析受信任的用户上下文、权限表达式和安全异常，避免 Gateway、Core、IoT 各写一套不一致的安全代码。

### 后台管理接口与权限规范

- **接口路由与端点统一规范**：所有后台管理接口统一使用 `/api/auth/admin` 前缀：
  - 租户设置端点统一为 `GET/PUT /api/auth/admin/tenants/current`；
  - 重置密码端点统一为 `POST /api/auth/admin/users/{id}/reset-password`（请求体字段为 `newPassword`）；
  - 用户分页列表查询入参统一为 `page`, `size`, `roleId`（支持按角色分页筛选用户）；
  - 角色管理端点：`GET/POST /api/auth/admin/roles`、`PUT/DELETE /api/auth/admin/roles/{id}`、`GET/PUT /api/auth/admin/roles/{id}/permissions`、`GET/PUT /api/auth/admin/roles/{id}/menus`；
  - 权限目录端点：`GET /api/auth/admin/permissions`；
  - 菜单管理端点：`GET /api/auth/admin/menus`（树）、`GET /api/auth/admin/menus/{id}`（详情）、`POST/PUT/DELETE /api/auth/admin/menus/{id}`，以及 `PUT /api/auth/admin/menus/{id}/status`（仅处理 `status`）。普通 `PUT` 负责 `menuCode`、`visible` 等菜单字段。
- **权限编码冒号规范**：所有权限编码统一采用冒号分段格式（如 `auth:user:view`、`auth:user:create`、`auth:role:edit`、`inv:balance:view` 等）。
- **权限目录只读**：权限目录是系统内置只读目录（常量池），不允许管理员动态增删权限编码；由角色负责汇聚权限点进行授权。
- **权限与菜单解耦**：角色一方面绑定权限点（Role-Permission），另一方面绑定可见菜单项（Role-Menu），实现功能权限与前端菜单展示的清晰解耦。
- **授权分配严格全量 ID 前置校验**：在为用户分配角色、为角色分配权限点/菜单时，后端必须一次性校验全量目标 ID 的存在性、当前租户归属、`isdel = 0` 和 `status = ACTIVE`。一旦检测到任何非法 ID、跨租户 ID、已删除或已停用 ID，必须在删除旧关联前拒绝本次操作并整体回滚事务，杜绝部分写入。
- **菜单字段语义分离**：`visible` 仅控制导航展示，`status` 仅控制菜单是否可用；两者必须分别持久化、分别回读，菜单编码修改必须执行当前租户内有效唯一性校验。

### JWT、数据库与 Redis

- JWT 只携带最小身份信息，至少包含用户标识 `sub` 和会话标识 `jti`；角色、权限等可变信息不固化进 JWT。
- PostgreSQL 中的用户、角色、权限及其关系是事实来源。
- Redis 仅作为用户权限上下文的高速缓存，并保存账号当前有效 `jti` 等会话状态；缓存丢失或过期后可从数据库重建。
- 同一账号一期只允许一个有效会话。新登录成功后替换旧 `jti`，旧 Token 后续请求返回 `401`。
- 业务上允许企业自行共享账号，但系统只审计账号、`jti`、时间和请求信息，不承诺识别共享账号背后的自然人。

## 角色与权限基线

一期固定六类业务角色；一个账号可以具有多个角色，功能权限取角色并集，数据范围仍限定当前租户。

| 角色 | 主要职责 |
| --- | --- |
| 租户管理员 | 当前租户内的账号、角色、权限授权、菜单绑定及租户基础设置；不自动拥有全部业务操作权限 |
| 销售人员 | 客户和销售订单的创建、提交、审核、进度跟踪及人工完成 |
| 采购人员 | 供应商和采购订单的创建、生产来源关联、提交、审核、进度跟踪、供应方退回决定与协调及人工完成 |
| 仓库人员 | 到货外观验收、收货前拒收、实际接收、质量处置实物执行、上架、直接拣货、发货、异常退回/释放、生产领退料确认和成品入库确认 |
| 生产质检人员 | BOM（物料清单）、工艺路线、工单、派工、工序执行、报工、采购到货质量检验、放行/报废决定、生产质检以及生产侧领退料/成品入库单创建 |
| IoT人员 | 设备、凭证、遥测、状态、告警确认及业务上下文补充 |

- **一期无平台超级管理员**：当前一期不存在跨租户的平台超级管理员，所有管理操作均在租户上下文内执行。
- **租户管理员数据边界**：租户管理员只管理当前租户内的数据，不可跨租户访问或修改任何数据。
- 一期不增加“主管/领导”技术层级。销售订单审核仍属于销售人员权限，采购订单审核仍属于采购人员权限。
- 企业可在业务上约定某个同角色账号专门审核，系统记录实际操作账号和会话，但技术上不限制为指定账号。
- 同一角色内的账号默认拥有该角色已配置的全部功能权限；若未来需要岗位细分，再新增权限组合，而不是在一期引入隐藏的账号特判。
- 质量处置采用“业务决定 + 仓库执行确认”：生产质检人员决定放行或报废，采购人员决定并协调退回供应方，仓库人员确认实际移位、退回出库或报废扣减。
- 生产领料和成品入库均由生产质检人员创建业务单据、仓库人员确认实物变化；工单审核、派工和工序执行不需要采购人员或仓库人员参与。

## 横切约束
- **单库多租户与模块划分**：
  - 各服务共用同一个 PostgreSQL 数据库实例及 `public` schema；
  - 通过表前缀（认证与权限 `auth_`、主数据 `md_`、仓储与库存 `inv_`、设备与物联网 `iot_` 等）进行模块物理划分；
  - 各模块使用独立的 Flyway 版本历史表（如 `auth_flyway_schema_history`、`core_flyway_schema_history`、`iot_flyway_schema_history`）独立演进；
  - 核心业务表与认证表必须包含 `tenant_id`，严格按当前租户隔离数据；
  - **Flyway V5 迁移与菜单多租户隔离**：通过 Flyway V5 迁移在 `auth_menu` 表中增加 `tenant_id`、`visible`、`status` 字段；历史菜单回填到既有租户 `a0000000-0000-0000-0000-000000000001`，第二演示租户使用 `a0000000-0000-0000-0000-000000000002`，有效菜单编码唯一约束为租户内 `(tenant_id, menu_code)`；迁移仍使用同一 `public` schema，历史表接管不删除旧共享表。
  - **统一逻辑软删除**：关联数据及核心实体统一采用逻辑软删除（`isdel = 1`），禁止物理 `DELETE`，查询必须强制过滤 `isdel = 0`。
- 模块只能通过应用服务或受控 API 访问其他模块能力，严禁跨模块直接读写底层数据库表
- 所有关键写操作需要幂等策略
- 库存变化只能通过库存应用服务完成，禁止其他模块直接修改 `InventoryBalance`
- IoT 先独立保存设备事实，Core 暂时不可用不得导致已接收遥测或告警丢失
- 一期优先使用清晰的同步接口完成主业务闭环，只在 MQTT 设备接入边界使用消息协议
- 通用 Outbox + RabbitMQ 可靠事件传播放入二期
- AI 工具默认只读，按租户和权限过滤数据

## 服务端口
- Gateway：`20001`
- Auth：`10002`
- Core：`10003`
- IoT：`10004`

## 本地开发环境基线
- 当前本机开发实例使用 Java 21、Maven 3.9.1、Node 20 与 PostgreSQL 12.1（`127.0.0.1:5433/ai_learn`）；SQL/Flyway 兼容性以下限 12.1 为准，文档中出现的“12.1及以上兼容”仅表示可兼容更高版本，不改变当前基线。
- 参考工程可继续保留各自的 Node 22 与 PostgreSQL 12.1 及以上兼容配置；其中出现的历史端口或高版本示例不代表当前项目事实。
