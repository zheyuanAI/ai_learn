# 制造与仓储协同执行平台项目计划

> 版本：1.0
>
> 日期：2026-08-20
>
> 状态：已批准，作为一期设计、开发与验收基线
>
> 适用范围：`ai_learn_developProject` 一期设计、开发与验收

## 1. 项目定义

本项目建设一个面向中小型离散制造场景的轻量化制造与仓储协同执行平台。项目采用“边开发、边学习”的方式，以一条可运行、可验证、可追溯的黄金业务闭环为主线，学习并实践 ERP、WMS、MES、IoT、二维可视化与 AI 只读助手之间的业务边界和协同方式。

项目不是完整 ERP、通用 IoT 平台或生产级工业套件。它重点解决业务需求进入企业后，采购、库存、生产、仓储和设备事实彼此割裂，导致订单执行进度不透明、库存不可信、异常难定位和过程难追溯的问题。

项目核心定义为：

> 以制造与仓储的协同执行链为核心，由单据表达业务意图，由显式状态和领域操作控制执行，由库存流水、工序执行、报工、质检、遥测与告警记录业务事实，使订单从需求到交付的关键过程可核对、可追溯、可发现异常。

## 2. 目标企业假设

一期采用以下教学型企业场景作为统一设计假设：

- 单工厂、一个或少量仓库的中小型离散装配制造企业；
- 仓库以人工或半自动操作为主；
- 采购、销售、生产和仓库之间主要依靠 Excel、纸质单据或即时通讯协作；
- 企业缺少统一可信的库存、生产执行和设备异常关联视图；
- 一期使用模拟设备通过 MQTT 上报数据，不依赖真实 PLC。

该假设用于约束一期范围，不代表所有制造企业。若后续获得真实企业案例，应先验证业务语义，再调整领域规格。

## 3. 企业痛点与预期价值

| 企业痛点 | 一期能力 | 预期结果 |
| --- | --- | --- |
| 销售、采购、生产和仓库各自维护数据 | 建立人工供需关联和黄金业务闭环 | 能说明工单和采购因何产生，并追踪订单执行进度 |
| 实物、预留和可用库存混淆 | 建立库存余额、预留、移动和流水内核 | 能解释当前库存是多少、在哪里、为何变化 |
| 重复操作或并发操作导致库存错误 | 事务、幂等和基本并发控制 | 关键库存命令重复调用结果一致，可用库存不为负 |
| 生产与仓库只在成品入库时连接 | 增加生产领料、退料和成品入库 | 原料出库、生产执行和成品回库形成闭环 |
| 工单状态不能说明现场真实执行 | 区分工单、派工、工序执行、报工和质检 | 能追踪人员、设备、工序、数量和时间 |
| 设备告警脱离生产上下文 | 区分遥测、设备状态和告警，并关联工序执行 | 能说明设备异常可能影响的工序和工单 |
| 异常依靠人工发现和追问 | 统一异常查询视图、看板和二维地图 | 能快速定位库存、生产和设备异常 |
| 管理查询依赖人工汇总 | 权限约束的 AI 只读工具 | 能以自然语言查询可信业务事实并保留审计 |

## 4. 核心设计原则

### 4.1 意图、执行与事实分离

- 采购订单、销售订单和生产工单表达业务意图；
- 上架、拣货、派工和质检保留各自领域语义，不抽象成万能任务；
- 库存流水、工序执行、报工、质检、遥测和告警记录实际发生的事实；
- 看板、地图、追溯和 AI 仅查询或表达事实，不建立第二套事实来源。

### 4.2 业务闭环优先于功能数量

一期优先跑通一条黄金业务闭环。与闭环无关、不能改变或解释业务事实、无法通过场景验收的功能延后处理。

### 4.3 显式状态迁移

一期不引入 BPM 或通用工作流引擎。每个领域对象通过后端显式校验“当前状态 + 用户权限 + 业务条件”决定操作是否合法，前端按钮只反映后端能力，不承担最终业务控制。

### 4.4 先具体、后抽象

一期不设计万能任务表、万能业务关系表和统一异常明细表。领域关系首先落在具体业务模型中，再通过只读模型聚合为追溯和异常视图。

### 4.5 物理单体、逻辑模块化

一期保留 Gateway、Auth、Core、IoT 四服务，不继续拆分采购、销售、库存、制造、质量和 AI 服务。Core 内部按领域模块组织，模块之间通过应用服务调用，禁止跨模块直接修改对方数据。

## 5. 黄金业务闭环

一期以以下场景作为最高优先级主线：

```text
销售订单产生 100 件产品需求
        ↓
人工判断现货与生产需求，并建立来源关联
        ↓
创建生产工单，人工关联销售订单行
        ↓
根据 BOM 判断原料不足，人工创建并关联采购订单
        ↓
采购收货确认，库存进入收货暂存位
        ↓
上架到目标库位，企业总库存不变
        ↓
生产领料确认，仓库库存减少并记录领料事实
        ↓
派工并开始工序执行
        ↓
模拟设备上报遥测；异常时生成告警
        ↓
告警在 IoT 内独立保存，再关联当前工序执行
        ↓
恢复后继续执行，完成报工和质量检验
        ↓
合格品完成成品入库
        ↓
销售订单预留库存、拣货并发货确认
        ↓
完成交付并可追溯全过程
```

一期只提供人工供需关联，不实现自动 MRP、自动缺口计算、自动工单生成或自动采购建议。

## 6. 一期能力范围

### 6.1 身份、租户与权限

- 登录、用户、角色、菜单和权限；
- 单库多租户隔离；
- 关键操作审计；
- AI 工具沿用普通用户的数据权限。

### 6.2 基础资料

- 客户、供应商、产品、计量单位；
- 仓库、收货暂存位、发货暂存位和普通库位；
- BOM、简化工艺路线、工序和工作中心；
- 设备、设备模型、生产区域和二维地图点位。

一期只建设黄金闭环必需的基础资料，不追求完整主数据平台。

### 6.3 人工供需关联

- 生产工单可人工选择来源销售订单行；
- 采购订单或采购明细可人工关联来源生产工单或原料需求；
- 关联只用于来源说明、进度汇总和追溯；
- 一期不自动计算需求数量，不合并多订单需求，不实现计划运算。

供需关联不单独建设一个空泛模块，其字段和规则分别落在销售、生产和采购领域中，由追溯只读模型统一展示。

### 6.4 库存事实内核

库存内核至少包含：

- `InventoryBalance`：按租户、产品、仓库、库位和可选批次保存当前快照；
- `InventoryReservation`：保存销售等业务对库存的预留；
- `InventoryTransaction`：记录不可随意修改的库存变化事实；
- 库存移动：记录产品在暂存位、普通库位和发货暂存位之间的位置变化。

一期统一使用以下数量语义：

- `on_hand_qty`：企业当前持有并纳入库存管理的实物数量；
- `reserved_qty`：已被业务预留但尚未发货的数量；
- `available_qty = on_hand_qty - reserved_qty`；
- `available_qty` 任何时候不得小于零。

一期统一采用业务术语“库存预留”和字段名 `reserved_qty`；领域规格、API、原型和验收用例均不得再引入同义的第二套库存占用字段。

关键库存时点固定如下：

| 业务动作 | 企业总实物库存 | 预留库存 | 位置库存 |
| --- | --- | --- | --- |
| 收货确认 | 增加，进入收货暂存位 | 不变 | 收货暂存位增加 |
| 上架确认 | 不变 | 不变 | 暂存位减少、目标库位增加 |
| 销售预留 | 不变 | 增加 | 不变 |
| 拣货确认 | 不变 | 不变 | 原库位减少、发货暂存位增加 |
| 发货确认 | 减少 | 释放对应预留 | 发货暂存位减少 |
| 生产领料确认 | 减少 | 不变 | 原料库位减少 |
| 生产退料确认 | 增加 | 不变 | 退回库位增加 |
| 成品入库确认 | 增加 | 不变 | 成品库位增加 |

“收货确认即纳入库存、上架只改变位置”是本项目一期的明确业务选择，不宣称是所有企业的唯一模式。

### 6.5 采购入库

- 采购订单创建、提交、审批和分批收货；
- 收货确认后在收货暂存位增加库存；
- 生成上架任务并移动到目标库位；
- 采购、收货、上架和库存流水可追溯。

### 6.6 销售出库

- 销售订单创建、提交和审批；
- 按库位检查并预留可用库存；
- 生成拣货任务并移动到发货暂存位；
- 发货确认后扣减企业实物库存并释放对应预留；
- 重复预留、重复拣货和重复发货必须被阻止。

### 6.7 制造执行

- BOM、简化工艺路线和工序定义；
- `WorkOrder` 表达生产意图，并可关联来源销售订单行；
- `DispatchOrder` 表达人员、设备、工序和数量的派工安排；
- `OperationExecution` 记录一次工序实际执行的开始、暂停、完成、人员、设备和时间；
- `WorkReport` 记录合格数量、不良数量和报工时间；
- `QualityInspection` 记录质量结果；
- `MaterialIssue`、`MaterialReturn` 连接原料仓库与生产执行；
- `FinishedGoodsReceipt` 将已检验合格数量转为成品库存。

一期不实现 WIP 库存、线边仓、自动排产、返工和复杂质检。

### 6.8 IoT 设备事实

- `DeviceProfile` 描述设备类型和允许的指标；
- `Device`、设备凭证和 MQTT 主题约定；
- `DeviceTelemetry` 保存带设备、时间戳和消息标识的原始遥测；
- `DeviceStatus` 保存在线状态、运行状态和最后通信时间；
- `DeviceAlarm` 与告警历史记录触发、确认和恢复；
- 使用 `device_id + message_id/sequence` 对 QoS 1 重复消息去重；
- IoT 必须先独立保存遥测、计算状态并保存告警，再异步或延后补充业务上下文；
- Core 暂时不可用时，不得导致已经收到的遥测和告警丢失。

设备优先关联工作中心或生产区域，工序执行可选关联设备。告警通过当时的设备和未完成工序执行关联生产上下文；若自动判断不可靠，允许人工补充关联。

### 6.9 追溯与异常视图

- 任意库存流水可追溯到源业务及明细；
- 生产工单可追溯领退料、派工、工序执行、报工、质检和成品入库；
- 销售订单可追溯人工供需关联、库存预留、拣货和发货；
- 设备告警可追溯设备、时间、工序执行和生产工单；
- 异常中心统一查询库存异常、生产异常和设备告警，但底层保持各自领域模型。

### 6.10 二维地图、看板与 AI

- 二维地图展示厂区、仓库、生产区域、设备点位和告警状态；
- 看板展示库存、订单、生产、质量、设备和告警摘要；
- AI 通过受控只读工具查询库存、订单、工单、告警和追溯信息；
- AI 回答展示来源摘要、时间范围和工具调用摘要；
- AI 不直接生成 SQL，不修改业务数据。

## 7. 项目特色

1. **菜单系统转向协同执行链**：采购、销售、库存、制造和设备围绕同一黄金业务闭环协作。
2. **库存不是可任意修改的数字**：余额用于查询，预留表达占用，流水记录事实，并支持余额一致性检查。
3. **单据、执行和事实分离**：工单不承载全部现场细节，工序执行、报工和质检记录实际结果。
4. **IT/OT 业务融合**：设备告警能够进入工序、工单和销售履约的业务上下文。
5. **IoT 事实独立可靠**：上层业务暂时不可用时，设备遥测与告警仍先保存。
6. **后端规则优先**：状态、权限、幂等和业务条件由后端保证，不依赖页面隐藏按钮。
7. **适合学习与演示**：通过模拟订单和模拟设备完成复杂度受控的跨域实践。
8. **AI 只读且可审计**：AI 是受权限约束的新查询入口，不是超级管理员。

## 8. 系统结构与边界

| 组件 | 端口 | 一期职责 |
| --- | ---: | --- |
| Frontend | 开发端口按 Vite 配置 | 业务页面、地图、看板和 AI 交互 |
| Gateway | 10001 | 统一入口、鉴权转发和异常包装 |
| Auth | 10002 | 登录、用户、角色、菜单、权限和租户上下文 |
| Core | 10003 | 采购、销售、库存、制造、质量、追溯、统计和 AI 只读工具 |
| IoT | 10004 | 设备、遥测、状态、告警和 MQTT 接入 |

Core 采用逻辑模块化结构：

```text
core
├─ purchasing
├─ sales
├─ inventory
├─ manufacturing
├─ quality
├─ traceability
├─ dashboard
└─ ai
```

服务可以使用同一 PostgreSQL 实例，但至少保持 Auth、Core、IoT 的 schema 和数据访问边界。禁止 IoT 直接关联查询或修改 Core 表，禁止业务模块直接修改 InventoryBalance，所有库存变化必须经过库存应用服务。

一期运行基线：Java 21、Maven 3.9.1、Spring Boot 3.3.5、Node 20、Vue 3、PostgreSQL 16（5433）、Redis（6379）和 Mosquitto（1883）。

## 9. 一期明确不做

- 完整财务、收付款、核销、账龄和总账；
- 自动 MRP、APS、产能日历和自动排产；
- 万能任务中心、万能业务关系表和 BPM 工作流引擎；
- WIP 库存、线边仓和复杂物料消耗模型；
- 复杂批次、序列号、保质期组合；
- 返工、重复质检和复杂质量体系；
- Modbus TCP、OPC UA 和真实 PLC 深度适配；
- 通用 Outbox、RabbitMQ 可靠事件平台；
- 三维数字孪生、Ditto 和 Cesium；
- RAG、知识库、文档解析和向量检索；
- 修改业务数据的 AI Agent；
- 生产级高可用、集群和容灾。

应收、应付草稿若保留，只作为业务追溯附属结果，不进入黄金闭环的核心验收。

## 10. 交付路线

当前正式开发周期为一个月，按四周完成一期黄金业务闭环。不以牺牲业务不变量换取表面进度；若学习或实现超出预期，优先削减二期展示能力，不削弱库存不变量和黄金闭环。

| 周期 | 主题 | 主要交付 | 阶段门槛 |
| --- | --- | --- | --- |
| 第 1 周 | 工程底座与库存内核 | 工程底座、最小认证与租户边界、主数据、库存内核 | 可用库存不为负，变化均有来源；规格、原型和权限边界一致 |
| 第 2 周 | 采购、销售与仓储闭环 | 采购收货/上架、销售预占/拣货/发货、人工供需关联 | 收货只增加一次、上架只移动位置；预占不改实物、发货才扣减实物 |
| 第 3 周 | 制造执行与 IoT 事实 | 工单、领退料、工序执行、成品入库、IoT 设备事实 | 制造意图与现场事实可区分；重复消息不重复生成事实，Core 故障不丢采集事实 |
| 第 4 周 | 追溯、轻量体验与验收 | 跨域追溯、轻量 GIS/看板/AI、异常验证、端到端验收 | 黄金闭环可追溯；轻量展示层只读且不建立第二套事实；架构级验收通过 |

每个阶段的完成定义包括：领域学习记录、术语确认、规格、原型、接口契约、实现、自动化测试和人工验收说明。

## 11. 验收标准

### 11.1 黄金闭环验收

- 销售订单行可人工关联生产工单；
- 生产工单可人工关联采购来源；
- 采购收货和上架后原料库存正确；
- 生产领料、工序执行、报工、质检和成品入库可完整执行；
- 设备异常不会丢失，并可关联到执行中的工序；
- 合格成品可以完成销售预留、拣货和发货；
- 从销售订单、生产工单、库存流水或设备告警任一点均可追溯关键上下游。

### 11.2 一期五项架构硬性验收

1. **库存事实完整**：每次余额或预留变化都有对应库存流水或预留记录，上架不重复增加总库存，拣货不等于发货。
2. **库存安全**：事务、幂等和基本并发控制共同保证 `available_qty >= 0`，相同业务命令重复调用不重复产生事实。
3. **状态与租户安全**：非法状态迁移由后端拒绝，租户 A 永远不能读取或关联租户 B 的业务数据。
4. **IoT 事实可靠**：QoS 1 重复消息不重复生成遥测或告警事实，Core 暂时不可用不影响 IoT 保存已经收到的数据。
5. **追溯可信**：任一库存流水可回到明确的源业务，黄金闭环的关键关联不存在仅供展示的孤立关系。

### 11.3 工程验收

- 后端关键领域规则有自动化测试；
- 前端类型检查和生产构建通过；
- Docker Compose 或本地文档可从零启动主要依赖和服务；
- 每个领域都有规格、API 契约、原型和验收清单；
- 演示数据和演示脚本可以稳定复现黄金闭环。

## 12. 项目风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 一期范围再次膨胀 | 以黄金闭环和五项架构硬验收为准，GIS、看板、AI 优先降级 |
| 供需关联演变成 MRP | 只做人工来源关联，不做自动需求运算 |
| 领域抽象过早 | 保留上架、拣货、工序执行、质检等具体模型 |
| 微服务复杂度遮蔽业务学习 | 四服务结构冻结，Core 内部逻辑模块化 |
| 库存时点理解不一致 | 以第 6.4 节库存时点表为一期唯一业务规则 |
| IoT 与 Core 强耦合 | IoT 先保存设备事实，业务上下文延后补充 |
| 页面完成但业务未闭环 | 每阶段以场景和不变量验收，不以页面数量验收 |

## 13. 沟通与变更机制

- 每次只设计和实现一个可验收闭环；
- 遇到业务术语、库存时点、状态迁移、跨域关联和范围变化时，必须先沟通确认；
- 普通实现细节采用最小可行方案并在阶段总结中说明；
- 新需求必须说明其对应痛点、目标角色、业务事实和验收场景；
- 无法推动黄金闭环、增强事实可信度或改善异常追溯的需求，默认进入二期候选；
- 已确认的核心术语维护在项目根目录 `CONTEXT.md`；
- 正式领域规则继续维护在各领域 `领域模型.md`，接口与验收分别维护在 `接口契约.md` 和 `验收标准.md`。

## 14. 评审意见吸收结论

正式计划采纳：人工供需关联、库存余额/预留/流水分层、库存关键时点、事务幂等并发控制、工单与工序执行分离、生产领退料、IoT 三类事实、MQTT 去重、IoT 独立保存、模块化 Core、黄金闭环和架构级验收。

正式计划裁剪：不做自动 MRP；不单独建设空泛 Fulfillment 模块；不引入万能任务、万能关系、统一异常明细表和 BPM；设备与工序的自动关联允许人工补充；一期只保留五项架构硬性验收，其余能力按阶段逐步增强。

本计划已同步到项目级规格、领域规格、原型和实施路线。后续范围或业务语义调整必须同时更新相关事实源；无论规格完成度如何，当前已实现能力始终以实际代码和配置为准。
