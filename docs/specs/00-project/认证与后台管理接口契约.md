# 认证与后台管理接口契约

> 当前状态：阶段0-1 代码级修复与本地回归已完成；真实 PostgreSQL 12.1 迁移和前端/人工联调仍为条件项。本文是接口事实源，不将代码级回归结果等同于最终现场验收。

## 1. 统一边界

- 所有后台管理接口使用 `/api/auth/admin/**`，只在当前租户上下文内读写。
- 一期只支持租户管理员，不增加平台超级管理员。
- 所有实体和关联数据遵守逻辑删除约定：有效数据为 `isdel = 0`。
- 数据库使用同一个 PostgreSQL 12.1 实例的 `public` schema；Auth 使用独立历史表 `auth_flyway_schema_history`，SQL/Flyway 兼容性以下限 12.1 为准。

默认演示租户 ID 为 `a0000000-0000-0000-0000-000000000001`，第二演示租户 ID 为 `a0000000-0000-0000-0000-000000000002`。

`POST /api/auth/logout` 仅注销当前请求已验证的 JTI；即使旧注销请求在通过鉴权后与同账号新登录交错，也不得撤销新登录的会话或清除其权限快照。Redis 的 JTI 比较与会话、权限、菜单缓存删除必须原子执行；账户管理或租户停用引发的强制全局撤销仍遵循各自接口规则。登录和租户停用在同一租户行上串行化：登录拿锁后重读租户状态，停用拿锁后才撤销会话与权限快照，确保停用完成后不会有迟到的登录发布新会话。

## 2. 菜单管理

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/auth/admin/menus` | 查询当前租户未删除菜单树（包含 `ACTIVE`/`DISABLED` 状态） |
| GET | `/api/auth/admin/menus/{menuId}` | 查询菜单详情 |
| POST | `/api/auth/admin/menus` | 创建菜单 |
| PUT | `/api/auth/admin/menus/{menuId}` | 修改菜单，包括 `menuCode`、`menuName`、层级、路由、组件、图标、排序、`visible` |
| PUT | `/api/auth/admin/menus/{menuId}/status` | 修改启停状态，仅处理 `status` |
| DELETE | `/api/auth/admin/menus/{menuId}` | 逻辑删除菜单；有子菜单或角色关联时返回业务冲突 |

创建和修改菜单的关键字段如下：

```json
{
  "parentId": null,
  "menuCode": "sys_user",
  "menuName": "用户管理",
  "routePath": "/system/users",
  "componentPath": "views/system/UserList.vue",
  "icon": "UserOutlined",
  "sortOrder": 1,
  "permissionCode": "auth:user:view",
  "visible": true
}
```

`menuCode` 在当前租户有效菜单中唯一，修改时必须真实持久化并可通过详情回读。菜单创建、改父级和删除在同一租户内应先串行化层级写入再读取父子关系，防止并发交叉改父级成环或新建子菜单与删除父节点交错。`visible` 只控制导航展示，不代表菜单是否可用；`status` 只能是 `ACTIVE` 或 `DISABLED`，通过启停接口单独修改。例如：

```json
{"status":"DISABLED"}
```

菜单树和详情返回 `visible`、`status`。前端 `MenuItem` 与后台管理菜单节点必须展示 `status`，不能以 `visible` 代替启停状态。

`GET /api/me/menus` 返回用户角色绑定的候选菜单树。侧边栏渲染时必须继续使用 `/api/me` 的当前权限集合与前端路由 `requiredPermission` 做交集过滤：无页面访问权限的叶菜单不展示，过滤后为空的父级分组也不展示。该过滤只改善导航可见性，直接访问地址仍由路由守卫及后端鉴权拒绝。

## 3. 用户、角色与授权

用户角色全量替换：`PUT /api/auth/admin/users/{userId}/roles`，请求体为 `{"roleIds": []}`；角色菜单全量替换：`PUT /api/auth/admin/roles/{roleId}/menus`，请求体为 `{"menuIds": []}`。

每次分配前必须一次性校验请求中的全部 ID：对象存在、属于当前租户、`isdel = 0` 且 `status = ACTIVE`。任一 ID 非法、跨租户、已逻辑删除或已停用时，整体拒绝本次请求，并且不得先删除旧关联或写入部分新关联。

## 4. Flyway 接管

现有共享 `public.flyway_schema_history` 的 V1-V4 记录必须按 Auth 脚本精确确认后，复制到 `public.auth_flyway_schema_history`；不删除旧表、不重放 V1-V4、不在当前开发数据库执行 V5/V6。切换配置后仅由 Auth 执行后续迁移。快速回归继续使用 H2，真实迁移验证使用隔离 PostgreSQL 12.1 临时实例或兼容容器。可执行 SQL 与步骤见 `deploy/postgres/auth-flyway-history-handoff.sql` 和 `deploy/postgres/README.md`。
