# 认证与后台管理验收标准

> 当前状态：阶段0-1 代码级修复与本地回归已完成；真实 PostgreSQL 12.1 迁移、连续 clean 回归、前端构建和人工验收仍需按环境条件补跑。以下仍是完整验收条件，不将本地回归结果等同于最终现场验收。

## 1. 数据库迁移

- 在隔离 PostgreSQL 12.1 全新数据库中，V1、V2、V3、V4、V5 顺序执行成功；若使用更高版本，只能作为“12.1及以上兼容”补充验证，不能替代 12.1 基线结果。
- 在隔离 PostgreSQL 12.1 中模拟已执行 V1-V4 的数据库，完成历史表安全接管后只执行 V5 成功。
- V5 首先移除 V1 的全局 `uq_auth_menu_code_active`，再插入第二租户同编码菜单；历史菜单回填到既有租户 `a0000000-0000-0000-0000-000000000001`。
- `auth_menu.tenant_id` 为 `NOT NULL`；`visible` 有明确默认值和合法值约束；`status` 默认 `ACTIVE` 且只允许 `ACTIVE`/`DISABLED`；有效菜单编码按租户唯一。
- 第二演示租户的租户、管理员角色、菜单和角色菜单关联全部使用 `a0000000-0000-0000-0000-000000000002`。

## 2. 菜单业务

- 菜单创建、树查询、详情查询、修改、逻辑删除、显隐切换和启停均真实落库并可回读。
- `PUT /api/auth/admin/menus/{id}/status` 修改 `status`，不能用 `visible` 冒充。
- `menuCode` 修改执行当前租户有效唯一性校验并可回读。
- `visible` 与 `status` 分别生效，后台节点和前端 `MenuItem` 返回并展示 `status`。

## 3. 授权完整性

- 用户分配角色前一次性校验所有角色的存在性、当前租户、`isdel = 0`、`status = ACTIVE`。
- 角色分配菜单前一次性校验所有菜单的存在性、当前租户、`isdel = 0`、`status = ACTIVE`。
- 任一 ID 不合法时整体拒绝，旧关联保持不变，不产生部分写入。
- 测试必须使用真实租户 B 数据覆盖跨租户场景，并覆盖停用角色、停用菜单不可分配。

## 4. 测试环境与工程检查

- 快速回归与真实迁移测试必须分开：测试会话缓存使用隔离 database、测试容器或测试替身，不读取开发环境 Redis 的共享 JTI；快速回归继续使用 H2，真实迁移验证只使用隔离 PostgreSQL 12.1 临时实例或兼容容器。
- 必须执行并留存真实命令摘要：`mvn clean test`、第二次连续 `mvn clean test`、`mvn clean package`、`npm run build`、PG12.1 全新库迁移、PG12.1 V1-V4 升级、`git diff --check`。
- 必须确认未提交 Git、未修改 V1-V4、未操作当前开发数据库；真实迁移测试不得连接 `127.0.0.1:5433/ai_learn`。
- 前端文档使用实际 `/system/*` 路径，接口契约、架构文档、README 与代码保持一致。
