## 一、整体架构决策

- 一期保留 Gateway、Auth、Core、IoT 四个独立后端服务进程，端口分别为 `20001`、`10002`、`10003`、`10004`。
- **数据库与模块隔离机制**：服务共用同一个 PostgreSQL 实例及 `public` schema，通过表前缀（`auth_` 认证与权限、`md_` 主数据、`inv_` 仓储与库存、`iot_` 物联网设备）和独立的 Flyway 历史表（如 `auth_flyway_schema_history`）划分模块边界。
- `security-common` 是 Gateway、Core、IoT 共享的安全基础代码，不是独立服务，不占用端口；当前优先放在 `platform-shared` 的逻辑安全组件中。
- Core 是 ERP/WMS、MES、质量、追溯、看板和 AI 只读工具的业务核心，但不是其他服务的统一请求分发中心。
- IoT 同时负责设备管控和 MQTT 接入、遥测、状态、告警事实。IoT 管控请求由 Gateway 直接路由到 IoT，并在 IoT 内完成方法级授权与业务规则校验，不需要先经过 Core。

## 二、认证与授权决策

- 目标技术体系采用 OAuth 2.0 / OpenID Connect 语义和 Spring Security；`platform-auth` 已具备基础认证与 5 大后台管理能力，当前修复尚未完成阶段验收。
- Gateway 负责统一入口、路由、JWT 签名/有效期/当前会话基础校验和粗粒度过滤。
- Auth 负责登录、用户、角色、功能权限、租户上下文、Token 签发及后台管理，是功能权限事实来源。
- Core、IoT 使用 Spring Security 方法级授权判断功能权限，并由具体业务模块继续校验当前租户、对象状态、数据范围和业务条件。
- JWT 只保存最小身份信息，至少包括 `sub` 和 `jti`；用户、角色、权限关系以 PostgreSQL 为事实来源。
- Redis 只保存可重建的权限高速缓存和账号当前有效 `jti` 等会话状态，不是用户权限事实数据库。
- 同一账号只允许一个有效会话。后登录替换前登录，旧 Token 后续请求返回 `401`。
- 企业业务上可以共享账号，但系统只审计账号、会话、时间和请求信息，不承诺识别共享账号背后的自然人。

## 三、角色与职责决策

一期固定六类角色：

| 角色 | 主要职责 |
| --- | --- |
| 租户管理员 | 当前租户账号、角色、权限、菜单和必要配置；不自动拥有全部业务权限 |
| 销售人员 | 销售订单创建、提交、审核、跟踪和人工完成 |
| 采购人员 | 采购订单创建、生产来源关联、提交、审核、跟踪、供应方退回决定与协调，以及人工完成 |
| 仓库人员 | 到货外观验收、收货前拒收、实际接收、质量处置实物执行、上架、直接拣货、发货，以及异常退回/释放和影响库存的生产领退料、成品入库确认 |
| 生产质检人员 | BOM（物料清单）、工艺路线、工单、派工、工序执行、报工、采购到货质量检验、放行/报废决定和生产质检，以及生产侧库存单据创建 |
| IoT人员 | 设备、凭证、遥测、状态、告警确认和业务上下文补充 |

- 生产人员和质检人员一期合并为“生产质检人员”。
- 不增加主管或领导技术层级。销售订单审核属于销售人员权限，采购订单审核属于采购人员权限。
- 企业可以约定同角色中的某个账号专门审核，但系统不做指定账号特判；审计记录实际操作账号和会话。
- 同角色账号默认拥有该角色配置的全部功能权限；账号多角色时功能权限取并集，数据范围仍为当前租户。
- 采购来源关联只由采购人员完成；仓库人员不负责判断采购需求来源。
- 采购到货由仓库人员验收并确认接收；质量检验由生产质检人员完成。放行或报废由生产质检人员决定，退回供应方由采购人员决定并协调，实际移位、退回出库或报废扣减由仓库人员确认。
- 生产领料由生产质检人员创建领料单、仓库人员确认发料；工单审核、派工和工序执行只属于生产质检人员。成品入库由生产质检人员创建入库单、仓库人员确认实物入库。

## 四、黄金业务闭环与业务事实

一期黄金业务闭环为：

```text
销售订单
  → 人工关联生产工单
  → 人工关联采购来源
  → 仓库到货外观验收（收货前可全部或部分拒收）
  → 实际接收数量全部进入质量隔离位
  → 采购到货质量检验与质量处置
  → 仓库确认质量处置和上架
  → 工单审核、生产领料、派工、执行、报工和质检
  → 成品入库申请与仓库确认
  → 销售直接拣货（内部自动预留）和发货
  → 看板、地图、追溯和 AI 只读查询
```

- 一期不实现自动 MRP、自动缺口计算、自动工单或自动采购建议。
- 预留只增加 `reserved_qty` 并减少可用量，不扣减 `on_hand_qty`。
- 直接拣货在同一事务内自动补足本次数量所需预留，再将实物与预留分配移动到 `ShippingStaging（发货暂存位）`，不扣减企业总实物库存。
- 发货确认才扣减实物库存，并释放本次对应预留。
- 收货前拒收数量不进入库存、不计入采购累计已收货并继续作为待收数量；只有实际接收数量增加库存。
- 仓库实际接收的货物全部进入 `QualityHold（质量隔离位：企业已经接收，但暂时禁止正常使用的受管库位）`；生产质检人员检验后，合格数量等待放行，不合格数量继续隔离并等待退回或报废。
- IoT 遥测、状态和告警先在 IoT 独立保存，再补充生产业务上下文。

## 五、人工完成决策

- 一期销售订单和采购订单都保留人工完成入口，允许处理小规模错误或实际业务终止。
- 销售订单人工完成由销售人员执行，释放剩余有效预留，不补造拣货、发货或库存流水。
- 采购订单人工完成由采购人员执行，表示剩余未收货数量不再履约，不补造收货、上架或库存流水；已经收货的合格货物仍可继续上架，质量待处置货物仍须完成放行、退货或报废。
- 人工完成必须记录完成方式、原因、账号、会话标识和时间。
- 已经发生的收货、上架、预留、拣货、发货和库存流水仍然保留，不得用人工完成覆盖历史事实。

## 六、销售订单已确认事项

- 销售订单页面将 `Draft（草稿）` 统一显示为“未提交”；只有“未提交”状态可以修改订单核心字段。
- 销售页面正常路径为“审核通过 -> 直接拣货 -> 发货”；允许分批直接拣货和分批发货，直接拣货内部自动形成等量预留。
- 订单明细累计记录 `ordered_qty`、`reserved_qty`、`picked_qty`、`shipped_qty`。
- 部分发货后可以继续履约，也可以由销售人员填写原因后人工完成剩余数量。
- 重复命令必须幂等，累计履约数量不得超过销售订单行允许履约数量。
- 销售订单采用双轴状态：持久化生命周期 `Draft -> Submitted -> Approved -> Completed`，查询时由明细数量派生 `NotStarted / InProgress / FullyShipped`。
- `Reserved`、`Picking`、`Shipped` 不再作为销售订单主状态；自动预留、拣货和部分发货期间生命周期保持 `Approved`。
- `fulfillment_status` 不持久化，订单行数量与库存事实是进度事实源。
- 人工完成前必须先退回未发货暂存数量，再释放剩余有效预留。
- 人工完成后页面主标签显示“已完成（人工）”，实际发货数量继续按事实展示，不得显示“全部发货”或补造完成数量。
- 完整业务规则见 `docs/specs/10-erp-wms/销售订单业务规则.md`。

## 七、其他模块已确认事项

- 库存：库存余额与库存流水分离；预留不扣实物库存，拣货只改变位置，发货才扣减实物库存；盘点状态为“未盘点 → 盘点中 → 已确认并调整”。
- 采购：支持分批到货外观验收、收货前全部/部分拒收、实际接收、采购到货质检、质量处置和分批上架；拒收不入库且继续作为待收数量，实际接收货物全部先进入质量隔离位，质检合格后放行、不合格继续隔离；人工完成只终止未收货余量，不阻断已收货货物的后续处理；报废必须填写原因并形成库存减少流水。
- 生产与质检：一个工单最多关联一个销售订单明细，同一销售订单明细可以拆成多个工单；工单状态为“未提交 → 待审核 → 已下达 → 生产中 → 已完成”，审核退回后为“审核拒绝”，未提交和审核拒绝均可修改并重新提交。
- IoT（物联网设备接入）：一期使用 MQTT（消息队列遥测传输协议）模拟设备接入，设备、遥测、状态和告警分离；默认离线阈值为 60 秒；同一“设备 + 规则”只保留一个活动告警，恢复可以先于人工确认。
- GIS（地理信息展示）与看板：使用二维底图和百分比坐标；同租户允许多张地图；状态展示优先级为“告警 > 离线 > 预警 > 正常”；看板默认展示今日数据，每 30 秒自动刷新，数据源失败时保留旧值并标记陈旧。
- AI 助手：一期为受权限约束的只读业务助手，不直接访问数据库、不执行写操作；通过 PokeAPI 中转站的 OpenAI Responses（响应式接口）兼容协议调用 Grok 模型，默认优先 `grok-4.6`，最终模型标识由部署配置决定；一期不启用 Grok 联网或 X 搜索。
- 模块级规则索引见 `docs/specs/00-project/全模块业务规则总览.md`。

## 九、阶段1 后台管理与权限体系已确认设计决策

阶段1已具备认证中心与 5 大后台管理模块（租户设置、用户管理、角色与权限/菜单授权、权限只读目录、菜单管理）的基础实现；当前正在修复迁移、菜单 CRUD/启停和授权原子校验，阶段验收尚未完成。关键设计决策冻结如下：

1. **多模块数据存储与 Flyway 独立管理**：
   - 后端服务共用同一个 PostgreSQL 实例及 `public` schema；
   - 通过严格的物理表前缀划分模块（`auth_` 认证、`md_` 主数据、`inv_` 仓储库存、`iot_` 物联网设备）；
   - 各模块使用独立的 Flyway 版本历史表（如 `auth_flyway_schema_history`）管理迁移脚本，互不干扰；
   - **Flyway V5 迁移与菜单多租户物理隔离**：通过 Flyway V5 迁移在 `auth_menu` 表增加 `tenant_id`、`visible`、`status` 字段；历史菜单回填到既有默认租户 `a0000000-0000-0000-0000-000000000001`，第二演示租户使用 `a0000000-0000-0000-0000-000000000002`，并以租户内有效菜单编码唯一约束实现多租户菜单物理隔离与显隐/可用状态控制。
2. **租户范围与管理员边界**：
   - **一期无平台超级管理员**：系统不存在跨租户的平台超管账号；
   - **租户硬隔离**：租户管理员（Role: `TENANT_ADMIN`）仅管理本租户数据与资源；所有后台管理接口、数据库增删改查均受 `tenant_id` 硬隔离约束。
3. **权限与菜单解耦及模型规范**：
   - **冒号分段权限编码**：权限编码统一采用冒号规范（如 `auth:user:view`、`auth:user:create`、`auth:role:edit`、`inv:balance:view` 等）；
   - **权限目录只读**：权限目录为系统内置常量字典（代码预置只读），不支持管理员在后台动态增删权限点；
   - **角色聚合授权**：角色是权限分配与菜单绑定的核心纽带。角色分别关联权限点（Role-Permission）与可见菜单（Role-Menu），用户通过赋予角色继承权限与动态菜单；
   - **授权分配严格全量 ID 前置校验**：用户分配角色、角色分配权限点与可见菜单时，后端严格一次性校验全量目标 ID 的存在性、当前租户归属、`isdel = 0` 和 `status = ACTIVE`；遇非法 ID、跨租户 ID、已逻辑删除或已停用 ID，必须在删除旧关联前整体拒绝操作。
   - **菜单字段语义分离**：`visible` 只表示是否在导航展示，`status` 只表示菜单是否可用（`ACTIVE`/`DISABLED`）；菜单编码修改必须校验当前租户内有效唯一性并真实持久化。
4. **统一逻辑软删除规范**：
   - 核心业务实体与关联数据（用户、角色、菜单等）统一采用逻辑软删除（`isdel = 1`，有效数据为 `isdel = 0`），禁止执行物理 `DELETE`；所有业务查询必须强制过滤 `isdel = 0`。
5. **安全保护与冲突校验（409 Conflict）规则**：
   - **防自删与防自我禁用**：当前登录的租户管理员禁止删除自身账号或将自身状态变更为禁用；
   - **最后管理员保护**：租户内必须保留至少一个启用的租户管理员，禁止删除或禁用最后一个租户管理员账号，禁止剥离最后一个管理员的管理员角色；
   - **409 冲突校验**：租户内用户名、角色编码重复时严格返回 409 Conflict；当角色已被用户绑定时禁止删除该角色（返回 409 Conflict）；当菜单存在子菜单节点时禁止删除父菜单（返回 409 Conflict）。
6. **后台管理接口统一规范**：
   - 后台管理接口统一使用 `/api/auth/admin/**` 前缀，包括：
     - **租户设置**：统一为 `GET/PUT /api/auth/admin/tenants/current`
     - **用户管理**：`GET /api/auth/admin/users`（分页入参统一为 `page`, `size`, `roleId`）、`POST /api/auth/admin/users`、`PUT /api/auth/admin/users/{id}`、`DELETE /api/auth/admin/users/{id}`（逻辑软删除 `isdel = 1`）、`POST /api/auth/admin/users/{id}/reset-password`（重置密码，入参字段统一为 `newPassword`）
     - **角色管理**：`GET/POST /api/auth/admin/roles`、`PUT/DELETE /api/auth/admin/roles/{id}`（逻辑软删除）、`GET/PUT /api/auth/admin/roles/{id}/permissions`（全量 ID 前置校验）、`GET/PUT /api/auth/admin/roles/{id}/menus`（全量 ID 前置校验）
     - **权限目录**：`GET /api/auth/admin/permissions`（只读）
     - **菜单管理**：`GET /api/auth/admin/menus`（树）、`GET /api/auth/admin/menus/{id}`（详情）、`POST/PUT/DELETE /api/auth/admin/menus/{id}`，以及 `PUT /api/auth/admin/menus/{id}/status`（启停）；普通 `PUT` 处理 `menuCode`、`visible` 等字段，删除仍为逻辑软删除并保留子菜单保护。

本轮 Flyway 历史表接管方案见 `deploy/postgres/README.md` 与 `deploy/postgres/auth-flyway-history-handoff.sql`：同一 `public` schema 内先复制既有共享 `flyway_schema_history` 中已确认属于 Auth 的 V1-V4 记录到 `auth_flyway_schema_history`，不删除旧表、不执行 V5，然后切换配置，仅由 Auth 执行 V5。当前开发数据库只执行到 V4，未在其上执行 V5；快速回归与真实迁移测试必须分开：快速回归继续使用 H2，真实迁移验证使用隔离 PostgreSQL 12.1 临时实例或兼容容器，且不得连接 `127.0.0.1:5433/ai_learn`。
