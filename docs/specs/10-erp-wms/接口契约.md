# ERP/WMS API 契约

> 本文同时记录目标与当前已冻结的 S2–S4 Core 路由；采购与销售后端已落地，S5/S6/S7 的制造、IoT、追溯/GIS/看板接口以对应领域契约和 READY 报告为准。前端联调与外部基础设施验证另行进行。

## 通用约束
- 所有写接口要求 `Authorization` 与 `Idempotency-Key`
- `tenant_id` 来自认证上下文，前端不得指定
- 写接口统一返回：`code`、`message`、`data`、`request_id`
- 库存命令返回余额、预留和位置变化摘要，并在同一事务内完成校验、变更和事实记录

- `GET|POST /api/warehouses`
- `GET|POST /api/locations`
- `GET|POST /api/uoms`
- `GET|POST /api/customers`
- `GET|POST /api/suppliers`
- `GET /api/inventory/balances`
- `GET /api/inventory/reservations`
- `GET /api/inventory/transactions`

### 库存事实查询
- 余额查询参数：`productId`、`warehouseId`、`locationId`、`lotNo`、`page`、`size`；返回 `InventoryBalancePage`，每行包含 `onHandQty`、`reservedQty`、计算后的 `availableQty`、`version` 和库存维度。
- 预留查询参数：`reservationId`、`sourceType`、`sourceId`、`sourceLineId`、`status`、`productId`、`warehouseId`、`locationId`、`lotNo`、`page`、`size`；返回预留及有效/历史分配。
- 流水查询参数：`transactionType`、`sourceType`、`sourceId`、`sourceLineId`、`productId`、`warehouseId`、`locationId`、`lotNo`、`occurredFrom`、`occurredTo`、`page`、`size`；流水只追加，位置移动同时返回来源和目标维度。
- 所有查询不接受客户端 `tenantId`，服务端从可信认证上下文过滤租户；分页 `page >= 1`、`1 <= size <= 200`。

## 采购入库
- `POST|GET /api/purchase-orders`
- `POST /api/purchase-orders/{id}/submit`
- `POST /api/purchase-orders/{id}/approve`
- `POST /api/purchase-orders/{id}/complete`
- `POST /api/purchase-receipts/confirm`（服务端按幂等键分配独立 `receiptId`）
- `POST /api/purchase-receipts/{id}/confirm`
- `POST /api/purchase-receipts/{id}/quality/inspect`
- `POST /api/purchase-receipts/{id}/quality/release`
- `POST /api/purchase-receipts/{id}/quality/return`
- `POST /api/purchase-receipts/{id}/quality/scrap`
- `POST /api/purchase-quality-dispositions/{id}/confirm`
- `POST /api/putaway-tasks/{id}/confirm`

### 创建采购订单
- 必填：`supplier_id`、`expected_arrival_date`、`lines`
- 明细必填：`product_id`、`ordered_qty`、`uom`、`target_warehouse_id`
- 明细可选：`source_work_order_id`，仅表达人工来源关联，不触发需求计算
- 创建后状态为 `Draft`，页面显示“未提交”；只有该状态允许修改供应商、产品、数量、计划到货日期和来源生产工单

### 确认收货

- 推荐入口为 `POST /api/purchase-receipts/confirm`：客户端只提交采购订单、收货时间、质量隔离库位和明细，服务端依据可信租户与本次 `Idempotency-Key` 分配独立 `receiptId`，并在响应 `PurchaseReceiptView.id` 返回；客户端不得用订单号、订单行 ID或随机 UUID代替。
- 必填：`receipt_time`、`quality_hold_location_id`、`lines`
- 明细必填：`product_id`、`arrived_qty`、`rejected_qty`、`received_qty`；启用批次时必填 `lot_no`
- 仓库到货验收只检查外观、型号和数量，数量必须满足 `arrived_qty = rejected_qty + received_qty`；不得在收货命令中提交质检合格或不合格数量
- `rejected_qty > 0` 时明细必填 `rejection_reason`；服务端记录操作账号、会话和时间
- `rejected_qty` 不增加库存、不计入采购累计已收货并继续保留为待收数量；允许 `received_qty = 0` 的全部拒收
- `received_qty` 全部进入 `QualityHold（质量隔离位）`，在完成采购到货质检和放行执行前不得参与正常预留、领料或上架
- 返回：`arrival_acceptance_summary`、`balance_delta_summary`、`inventory_transactions`
- 语义：只按 `received_qty` 增加企业实物库存；全部拒收时不产生库存变化或库存流水

### 确认上架
- 必填：`to_location_id`、`putaway_qty`
- 返回：`location_transfer_summary`、`inventory_transactions`
- 语义：只移动位置，不重复增加企业总库存
- 前置：本次数量已经收货且通过质量放行；采购订单已经人工完成不阻止已有合格货物继续上架

### 采购质量处置
- 检验：生产质检人员提交 `inspected_qty`、`qualified_qty`、`unqualified_qty` 与可选检验说明，且必须满足 `inspected_qty = qualified_qty + unqualified_qty`；累计检验数量不得超过对应收货明细的 `received_qty`，检验只生成质量事实且不改变库存
- 检验后：合格数量等待放行执行；不合格数量继续留在质量隔离位，等待退回供应方或报废决定
- 放行：生产质检人员提交 `disposition_qty` 与放行说明，生成 `PendingExecution（待执行）` 处置决定
- 退回：采购人员提交 `disposition_qty`、`reason` 与供应方处理说明，生成待执行处置决定
- 报废：生产质检人员提交 `disposition_qty`、`reason`，生成待执行处置决定
- 三类决定本身不直接改变库存；仓库人员调用 `POST /api/purchase-quality-dispositions/{id}/confirm` 确认实际处理
- 放行执行把对应实物从质量隔离位移到收货暂存位，之后通过独立上架任务上架；退回和报废执行减少质量隔离位实物库存并生成库存流水
- 放行累计数量不得超过质检合格数量；退回与报废累计数量不得超过质检不合格数量
- 检验、决定与执行确认均要求独立 `Idempotency-Key`；重复调用不得重复记录检验、占用可处置数量、移动或扣减库存

### 人工完成采购订单
- 必填：`completion_reason`
- 返回：`completion_type`、`remaining_unreceived_summary`、`audit_summary`
- 语义：剩余未收货数量不再履约，不补造收货、上架或库存流水
- 后续：已收货货物的上架和质量处置继续有效，不能因订单完成而删除或跳过
- 权限：采购人员；企业可约定专用审核/完成账号，但接口不做账号特判

## 销售出库
- `POST|GET /api/sales-orders`
- `POST /api/sales-orders/{id}/submit`
- `POST /api/sales-orders/{id}/approve`
- `POST /api/sales-orders/{id}/complete`
- `POST /api/sales-orders/{id}/reservations/release`
- `POST /api/pick-tasks/{id}/confirm`
- `POST /api/pick-tasks/{id}/return`
- `POST /api/sales-shipments/{id}/confirm`

### 查询销售订单
- 详情返回持久化 `status`、`completion_type`、完成审计字段和明细四类数量
- 详情动态返回 `fulfillment_status`、`unreserved_qty`、`unpicked_qty`、`shipping_staged_qty`、`active_reserved_qty`、`unshipped_qty` 与 `allowed_actions`
- `fulfillment_status` 不持久化；按 [销售订单业务规则](./销售订单业务规则.md) 计算

### 确认直接拣货
- 必填：`picked_qty`、`source_location_id`、`shipping_location_id`
- 返回：`auto_reservation_summary`、`location_transfer_summary`、`reservation_allocation_transfer_summary`
- 语义：先使用订单行已有的未拣预留，不足部分自动预留；再将实物和等量有效预留分配同步移动到发货暂存位，不改变企业总实物库存
- 事务：可用库存校验、自动预留、实物移动、预留分配移动和拣货事实必须全部成功或全部回滚，不允许留下本次自动预留但拣货失败的中间事实
- 一个销售订单允许产生多张拣货任务，以支持分批履约

### 退回未发货拣货
- 必填：`return_qty`、`to_location_id`
- 返回：`location_transfer_summary`、`reservation_allocation_transfer_summary`、更新后的订单行履约摘要
- 语义：将未发货实物及等量有效预留分配从 `ShippingStaging` 移回合法来源/拣货库位，减少订单行 `picked_qty`，不改变企业总实物库存或有效预留合计
- 权限：仓库人员；仅处理 `shipping_staged_qty` 范围内的数量；该接口属于异常处理，不作为页面正常履约步骤

### 异常释放未拣预留
- 必填：`release_lines`，明细包含 `sales_order_line_id`、`release_qty` 与原因
- 语义：只释放 `unpicked_qty（已预留但尚未拣货数量）`，增加可用库存但不改变企业总实物库存；已拣数量必须先退回
- 权限：仓库人员；该接口只用于退回后的终止、人工完成前清理或异常恢复，不作为页面正常履约步骤

### 确认发货
- 必填：`ship_time`、`shipment_lines`
- 明细必填：`sales_order_line_id`、`product_id`、`ship_qty`
- 返回：`balance_delta_summary`、`reservation_release_summary`、`inventory_transactions`
- 语义：扣减实物库存并释放对应预留
- 一个销售订单允许产生多张发货单；部分发货后保留剩余数量继续履约

### 人工完成销售订单
- 必填：`completion_reason`
- 返回：`completion_type`、`remaining_unfulfilled_summary`、`reservation_release_summary`、`audit_summary`
- 语义：终止剩余未履约数量并释放剩余有效预留；不补造拣货、发货或库存流水
- 前置：各订单行必须满足 `picked_qty = shipped_qty`；存在未发货暂存数量时先执行退回未发货拣货
- 权限：销售人员；企业可约定专用审核/完成账号，但接口不做账号特判
- 审计：服务端记录操作账号、`jti` 对应会话和完成时间，客户端不得自行指定这些字段

## 调拨与盘点
- `POST /api/transfers`
- `POST /api/transfers/{id}/confirm`
- `POST /api/stocktakes`
- `POST /api/stocktakes/{id}/start`
- `POST /api/stocktakes/{id}/confirm`

### 创建与确认调拨
- 创建请求：`transferNo`（可选）、`fromWarehouseId`、`fromLocationId`、`toWarehouseId`、`toLocationId`、`lines`。
- 调拨明细：`productId`、`lotNo`、`uom`、`quantity`；`quantity` 使用字符串并按 `NUMERIC(19,6)` 校验。
- 创建后为 `Draft`，只允许 `confirm`；确认仅通过 `InventoryCommandService.move` 在同一事务中完成来源扣减、目标增加和流水追加，成功后为 `Confirmed`，返回 `version` 与 `transactionIds`。
- 来源和目标库位不能相同；产品和批次身份不变；跨仓移动只允许 `TRANSFER` 交易语义；普通调拨不迁移预留。
- 权限：创建 `inv:transfer:create`，确认 `inv:transfer:confirm`。

### 创建、开始与确认盘点
- 创建请求：`stocktakeNo`（可选）、`warehouseId`、`locationId`（可选范围）；创建后为 `NotStarted`。
- 开始盘点：仅 `NotStarted` 可执行；按仓库/库位范围读取库存余额，保存每个产品/批次/库位的 `systemQty` 与 `systemBalanceVersion`，状态变为 `Counting`。
- 确认请求：`lines` 必须完整覆盖快照明细；每行提交 `lineId`、字符串 `countedQty`，差异时必填 `varianceReason`。
- 确认重新读取当前余额并校验版本和系统数量未变化，且 `countedQty >= reservedQty`；正差异调用库存 `increase`，负差异调用 `decrease`，交易类型固定为 `ADJUSTMENT`、来源类型为 `STOCKTAKE`。
- 确认成功后为 `ConfirmedAdjusted`，返回 `version`、每行 `varianceQty`、可选 `adjustmentTransactionId` 和 `transactionIds`；无差异保存确认事实但不产生库存流水。
- 权限：创建 `inv:stocktake:create`，开始 `inv:stocktake:start`，确认 `inv:stocktake:confirm`。
- 两类单据的写接口均要求 `Authorization` 和 `Idempotency-Key`；同一操作域、租户和 Key 的同载荷重试重放首次结果，不同载荷返回 409。

### 开始盘点
- 前置：盘点单为 `NotStarted`
- 结果：保存本次系统数量快照并进入 `Counting`

### 确认并调整
- 必填：盘点明细的 `counted_qty`；存在差异时必填 `variance_reason`
- 语义：按实盘数量与系统快照差异生成调整流水，并进入 `ConfirmedAdjusted`
- 无差异时保存确认事实但不生成数量变化流水

## 查询过滤
- 单据查询支持：`keyword`、`status`、`fulfillment_status`、`date_from`、`date_to`
- 库存查询支持：`product_id`、`warehouse_id`、`location_id`、`lot_no`、`transaction_type`、`source_type`、`source_id`
- 所有查询自动过滤 `tenant_id`

## 业务错误码
- `INV_001`：可用库存不足，直接拣货中的自动预留失败
- `INV_002`：重复命令命中幂等结果
- `INV_003`：余额版本冲突，请重试
- `INV_004`：目标库位不可用或库位类型不合法
- `INV_005`：预留与销售明细不匹配
- `PO_001`：采购单状态不允许当前操作
- `SO_001`：销售单状态不允许当前操作
- `SO_002`：销售订单行数量超过当前可操作上限
- `SO_003`：存在未发货暂存数量，不能释放对应预留或人工完成
- `ST_001`：盘点单状态不允许确认
- `PO_002`：收货、质量处置或上架累计数量超过允许上限
- `PO_003`：质量隔离货物尚未放行，禁止上架
- `PO_004`：到货/拒收/接收数量关系或质检合格/不合格数量关系不成立
- `PO_005`：收货前拒收数量缺少拒收原因
- `PO_006`：质量处置角色不匹配或处置尚未完成仓库执行确认
- `ST_002`：盘点差异缺少原因或调整流水生成失败

## 二期边界
- 不提供自动 MRP、自动采购建议、收付款、核销、账龄或完整财务接口
- 不提供序列号、保质期和复杂批次组合接口

## 阶段 2–7 后端正式契约冻结补充（2026-09-04）

本节以当前 `platform-core` Controller、DTO 和应用服务为准，覆盖本文前面的目标性描述；未列出的路由不作为本次后端对外承诺。阶段 0–1 的登录、权限和既有订单主链保持不变。

### 统一响应、格式和分页

- 成功和业务错误均使用 `{code,message,data,request_id,timestamp}`；成功 `code=200`，`request_id` 与 `X-Request-Id` 对应，时间为 ISO-8601 `OffsetDateTime`。
- UUID 使用标准字符串；采购/销售/调拨/盘点数量 DTO 使用字符串，按最多 6 位小数处理；库存和制造内部查询投影中的 `BigDecimal` 按 JSON 数字输出。
- 页面统一返回 `records,total,page,size,totalPages`，页码从 1 开始，服务端 `size` 最大 200；库存预留的 `records[*]` 为 `{reservation,allocations}` 嵌套视图。`content` 只保留 Java 内部兼容访问器，不出现在 HTTP JSON。
- 写接口必须带 `Authorization` 和 `Idempotency-Key`；租户、操作人、会话和审计时间从可信上下文补齐，客户端传入的租户字段不生效。

### S2 库存调拨、盘点和只读查询

正式路由：

- `GET /api/transfers?page=1&size=20&keyword=&status=`、`GET /api/transfers/{id}`
- `POST /api/transfers`、`POST /api/transfers/{id}/confirm`
- `GET /api/stocktakes?page=1&size=20&keyword=&status=`、`GET /api/stocktakes/{id}`
- `POST /api/stocktakes`、`POST /api/stocktakes/{id}/start`、`POST /api/stocktakes/{id}/confirm`
- `GET /api/inventory/balances`、`GET /api/inventory/reservations`、`GET /api/inventory/transactions`

调拨创建请求字段为 `transferNo,fromWarehouseId,fromLocationId,toWarehouseId,toLocationId,lines`，明细固定为 `productId,lotNo,uom,quantity`。响应 `data` 为 `TransferView`：`id,transferNo,fromWarehouseId,fromLocationId,toWarehouseId,toLocationId,status,version,confirmedBy,confirmedAt,lines,transactionIds,allowedActions`；明细另含 `id,lineNo`。状态只有 `Draft/Confirmed`，`allowedActions` 分别为 `[confirm]` 和 `[]`。

盘点创建请求为 `stocktakeNo,warehouseId,locationId`；确认请求只能使用 `{lines:[{lineId,countedQty,varianceReason}]}`，该嵌入式 `confirm` 是唯一盘点记录入口，不提供 `/record` 路由。响应 `StocktakeView` 包含 `id,stocktakeNo,warehouseId,locationId,status,version,startedBy,startedAt,confirmedBy,confirmedAt,lines,transactionIds,allowedActions`；明细包含 `systemQty,systemBalanceVersion,countedQty,varianceQty,varianceReason,adjustmentTransactionId`。状态为 `NotStarted/Counting/ConfirmedAdjusted`，允许动作依次为 `[start]`、`[confirm]`、`[]`。

库存查询正式参数为：余额 `product_id,warehouse_id,location_id,lot_no,page,size`；预留再加 `reservation_id,source_type,source_id,source_line_id,status`；流水再加 `transaction_type,source_type,source_id,source_line_id,occurred_from,occurred_to`。所有结果只在可信租户范围内返回。

### S3 采购收货、质量和上架

- `POST /api/purchase-receipts/confirm` 是服务端分配 `PurchaseReceipt.id` 的推荐入口；兼容入口 `POST /api/purchase-receipts/{receiptId}/confirm` 的路径参数仍是独立 `PurchaseReceipt.id`，不是采购订单 ID；请求体含 `purchaseOrderId,receiptNo,receiptTime,qualityHoldLocationId,lines`。
- `lines[*]` 固定含 `purchaseOrderLineId,productId,uom,arrivedQty,rejectedQty,receivedQty,lotNo,rejectionReason`，其中 `receiptTime` 为 ISO-8601 `OffsetDateTime`，三类数量均为最多 6 位小数字符串。
- 返回 `PurchaseReceiptView`：`id,receiptNo,purchaseOrderId,receiptTime,qualityHoldLocationId,status,confirmedBy,confirmedSessionId,confirmedAt,version,lines,arrivalAcceptanceSummary,balanceDeltaSummary,inventoryTransactions,allowedActions`；收货单状态为 `Draft/Confirmed`，确认后 `allowedActions=[]`。
- 不同到货批次使用不同 `receiptId`，订单累计收货由采购订单行聚合计算；`arrivedQty = rejectedQty + receivedQty`，拒收不产生库存流水，实际接收只进入 `QualityHold`。
- 质量决定和仓储执行分离：质检/质量处置使用现有 `/api/purchase-receipts/quality-inspections`、`/api/purchase-receipts/{id}/quality/inspect`、`/api/purchase-receipts/{id}/quality/{release|return|scrap}`、`/api/purchase-quality-dispositions/{id}/confirm`；上架使用 `GET /api/putaway-tasks`、`POST /api/putaway-tasks/{id}/confirm`，只允许 `ReceivingStaging -> Storage`。

### S4 销售履约

正式写路由为 `POST /api/pick-tasks/confirm`、`POST /api/pick-tasks/return`、`POST /api/sales-shipments/confirm`，以及保留独立 ID的兼容路由 `POST /api/pick-tasks/{id}/confirm`、`POST /api/pick-tasks/{id}/return`、`POST /api/sales-shipments/{id}/confirm`；另有 `POST /api/sales-orders/{id}/reservations/release`、`POST /api/sales-orders/{id}/complete`；读路由为 `GET /api/pick-tasks`。当前没有独立持久化 `pick_task` 或 shipment header：`pick-tasks` 列表返回 `SalesOrderPageResult`，推荐写路由由服务端依据可信租户和 `Idempotency-Key` 分配并返回 `operationId`，请求体中的 `salesOrderId` 是销售订单标识。

- 直接拣货请求为 `salesOrderId,lines[*]{salesOrderLineId,pickedQty,sourceLocationId,shippingLocationId}`；先自动补足预留，再把实物和有效预留分配移动到 `ShippingStaging`，不减少企业总实物库存。
- 退回请求为 `salesOrderId,lines[*]{salesOrderLineId,returnQty,toLocationId}`，只处理发货暂存且未发货数量。
- 释放请求为 `releaseLines[*]{salesOrderLineId,releaseQty,reason}`，只释放未拣预留；存在发货暂存时必须先退回。
- 发货请求为 `salesOrderId,shipTime,shipmentLines[*]{salesOrderLineId,productId,shipQty}`；确认时先释放对应有效预留，再扣减实物库存。
- 履约写操作返回 `SalesFulfillmentResult{action,operationId,order,inventoryTransactionIds,reservationIds}`。订单详情的 `allowedActions` 只使用 `directPick,ship,returnPick,releaseReservation,manualComplete`；未完成订单按当前数量返回 enabled，已完成订单返回空数组。
- 销售履约状态事实保持 `reservedQty/pickedQty/shippedQty/unpickedQty/shippingStagedQty/activeReservedQty/unshippedQty` 的数量关系；人工完成只释放未拣预留并保存原因，不补造拣货、发货或库存流水。

### S2–S4 稳定错误和不变量

除已有 `INV_*`、`PO_*`、`SO_*`、`ST_*` 外，当前冻结语义为：`INV_003` 表示余额版本冲突，`PO_002/PO_003/PO_004/PO_005/PO_006` 覆盖采购累计、质量隔离、数量关系、拒收原因和处置执行，`SO_002/SO_003` 覆盖履约数量及发货暂存约束，`ST_001/ST_002` 覆盖盘点状态、差异原因和调整流水。库存写事实只能经 `InventoryCommandService`，所有命令必须满足幂等、租户隔离、余额锁和可用量不为负。
