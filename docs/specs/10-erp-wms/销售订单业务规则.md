# 销售订单业务规则

> 状态：一期目标设计已确认  
> 决策日期：2026-08-28  
> 说明：本文是销售订单分批履约的业务规则事实源。接口当前仍是目标契约，不表示 Controller 已经实现。

## 1. 目标与边界

销售订单表达客户需求，页面正常履约采用“审核通过 -> 直接拣货 -> 发货”，支持分批直接拣货、分批发货和受控人工完成。库存预留作为直接拣货内部自动形成的底层事实保留，不作为页面正常步骤。状态模型必须同时满足两个目标：

- 用稳定、简洁的生命周期控制业务动作；
- 用明细数量准确表达可同时存在的预留、拣货和发货进度。

一期不实现自动 MRP、自动缺口计算、自动生产工单或自动采购建议。驳回、撤回和整单删除的业务规则在仓库内未发现事实依据，不进入本轮状态模型。

## 2. 角色职责

| 角色 | 允许动作 |
| --- | --- |
| 销售人员 | 创建、提交、审核、查看进度、人工完成销售订单 |
| 仓库人员 | 直接拣货、确认发货；异常时退回未发货拣货或释放未拣预留 |

前端隐藏按钮不能代替后端授权。每个写命令仍需校验功能权限、当前租户、订单状态、数量和库存条件。

## 3. 双轴状态模型

### 3.1 生命周期状态 `status`

`status` 是持久化字段，只控制订单是否允许继续执行相应动作：

```text
Draft -> Submitted -> Approved -> Completed
```

| 状态 | 语义 | 允许的核心动作 |
| --- | --- | --- |
| `Draft` | 未提交，可继续维护订单内容 | 修改、提交 |
| `Submitted` | 已提交，等待销售角色审核 | 审核 |
| `Approved` | 已审核，可执行仓储履约 | 直接拣货、发货、人工完成；异常时退回拣货或释放未拣预留 |
| `Completed` | 终态，不再允许新增履约事实 | 只读查询 |

自动预留、拣货和部分发货都不改变 `status`；订单在整个履约过程中保持 `Approved`。因此不再使用 `Reserved`、`Picking`、`Shipped` 作为销售订单生命周期状态。

### 3.2 履约进度 `fulfillment_status`

`fulfillment_status` 是 API 和页面使用的只读派生字段，不作为数据库事实源：

| 派生值 | 计算规则 |
| --- | --- |
| `NotStarted` | 所有明细的 `reserved_qty`、`picked_qty`、`shipped_qty` 均为 0 |
| `InProgress` | 已存在任一履约数量，且至少一行尚未全部发货 |
| `FullyShipped` | 每一行均满足 `shipped_qty = ordered_qty` |

`fulfillment_status` 只描述数量进度，不决定动作权限。人工完成后可能出现 `Completed + NotStarted` 或 `Completed + InProgress`；页面必须同时展示生命周期、履约进度和完成方式，不能只展示 `InProgress` 并暗示仍可继续操作。

### 3.3 完成方式 `completion_type`

- 非完成态：`completion_type` 为空；
- 全部订单行完成发货时：`completion_type = Normal`；
- 销售人员终止剩余未履约数量时：`completion_type = Manual`，且 `completion_reason` 必填。

## 4. 销售订单行数量语义

每个订单行保存：`ordered_qty`、`reserved_qty`、`picked_qty`、`shipped_qty`。

- `ordered_qty`：客户要求的订单数量；
- `reserved_qty`：当前仍被有效预留或已经进入下游拣货/发货的数量；
- `picked_qty`：当前仍在发货暂存位或已经完成发货的数量；
- `shipped_qty`：已经确认发货的累计数量。

由此可派生：

```text
unreserved_qty       = ordered_qty - reserved_qty
unpicked_qty         = reserved_qty - picked_qty
shipping_staged_qty  = picked_qty - shipped_qty
active_reserved_qty  = reserved_qty - shipped_qty
unshipped_qty        = ordered_qty - shipped_qty
```

每次成功命令后必须满足：

```text
0 <= shipped_qty <= picked_qty <= reserved_qty <= ordered_qty
```

这里的 `SalesOrderLine.reserved_qty` 是订单行履约口径，不等同于 `InventoryBalance.reserved_qty`。发货时，库存余额中的有效预留随本次发货释放；订单行的 `reserved_qty` 不回退，因为该数量已经进入更高的发货里程碑。

### 4.1 库位级预留分配

`InventoryReservation` 表达销售订单行的业务占用，`InventoryReservationAllocation` 表达这笔占用当前落在哪个仓库、库位和可选批次。每个库位的有效分配量计入对应 `InventoryBalance.reserved_qty`。

- 直接拣货时，系统先使用该订单行已有的未拣预留；不足部分在来源库位自动创建或增加有效分配；
- 上述预留补足与拣货必须在同一事务内完成，再将实物和等量有效预留分配从来源库位迁移到 `ShippingStaging（发货暂存位）`；
- 退回拣货时在同一事务内将实物和等量有效预留分配迁回合法来源/拣货库位；
- 拣货和退回只改变分配位置，不增加 `InventoryReservation.released_qty`；
- 主动释放或发货才减少有效分配并增加 `released_qty`；
- 每次迁移后，每个受影响库位仍须满足 `available_qty = on_hand_qty - reserved_qty >= 0`。

## 5. 核心业务动作

### 5.1 创建、提交与审核

- 创建后进入 `Draft`，页面统一显示为“未提交”；订单至少包含一条有效明细，每行 `ordered_qty > 0`；
- 只有“未提交”状态允许修改客户、产品、订单数量和计划发货日期等核心内容；提交后不得直接修改这些字段；
- 只有 `Draft` 可提交，提交后进入 `Submitted`；
- 只有 `Submitted` 可审核，审核后进入 `Approved`；
- 审核本身不自动预留库存，也不自动创建生产或采购单；仓库人员执行直接拣货时才自动建立本次所需预留。

### 5.2 分批直接拣货

- 仅 `Approved` 订单可直接拣货，本次 `picked_qty > 0`，且不得超过该行尚未拣货的订单数量；
- 系统优先使用该订单行已有的 `unpicked_qty（已预留但尚未拣货数量）`，不足部分自动预留；自动预留数量不得超过来源库位可用库存和该行 `unreserved_qty（尚未预留数量）`；
- 自动预留增加订单行与库存余额的 `reserved_qty（预留数量）`、减少 `available_qty（可用数量）`，但不改变企业总 `on_hand_qty（实物数量）`；
- 随后增加订单行 `picked_qty（累计拣货数量）`，并将本次实物及等量有效预留分配从来源库位同步移动到 `ShippingStaging（发货暂存位）`；
- 自动预留、数量校验、实物移动、预留分配移动和拣货事实必须在同一数据库事务中完成；任一步失败时整体回滚，不允许留下“已预留但本次拣货失败”的半成品事实。

### 5.3 异常退回与释放

- 退回拣货和释放预留不属于页面正常履约步骤，只在已拣货不再发出、人工完成前清理或异常恢复时使用；
- 仅 `Approved` 订单可执行异常退回或释放；
- 退回数量不得超过 `shipping_staged_qty（已拣货但尚未发货数量）`；退回将实物及等量有效预留分配从发货暂存位移回合法来源/拣货库位，并减少订单行 `picked_qty`；
- 释放数量不得超过 `unpicked_qty`，已经拣到发货暂存位的数量不能直接释放；
- 释放后订单行 `reserved_qty`、库存余额 `reserved_qty` 同步减少，`available_qty` 增加，`on_hand_qty` 不变；
- 如需释放已拣数量，必须先执行“退回未发货拣货”；退回本身只改变位置，不自动释放预留。

### 5.4 确认发货

- 仅 `Approved` 订单可发货；
- 本次 `ship_qty > 0`，且不得超过 `shipping_staged_qty`、对应有效预留和发货暂存位实物数量；
- 发货增加订单行 `shipped_qty`，同时减少发货暂存位的 `on_hand_qty`、库位级有效预留分配和企业总 `on_hand_qty`，并把本次数量记入业务预留的 `released_qty`；
- 发货不减少订单行 `reserved_qty` 或 `picked_qty`，因此数量不变量仍成立；
- 当所有订单行均全部发货时，服务端在同一事务内将订单置为 `Completed`，并记录 `completion_type = Normal`。

## 6. 人工完成

人工完成用于终止剩余未履约数量，不用于伪造正常履约。

- 仅销售人员可执行，且订单必须处于 `Approved`；
- `completion_reason` 必填，去除首尾空白后不能为空；
- 若任一行存在 `shipping_staged_qty > 0`，人工完成失败，必须先由仓库人员退回未发货拣货；
- 服务端在同一事务内释放剩余有效预留，使各行最终满足 `reserved_qty = picked_qty = shipped_qty`；
- 状态进入 `Completed`，记录 `completion_type = Manual`、原因、账号、会话标识和时间；
- 已发生的自动预留、异常释放、拣货、退回、发货和库存流水全部保留；
- 不补造剩余数量的拣货、发货或库存流水。

## 7. 命令幂等、并发与审计

- 所有写接口要求 `Idempotency-Key`；同一 `tenant_id + endpoint + Idempotency-Key` 重复调用返回首次成功结果；
- 同一幂等键携带不同业务载荷时必须返回冲突，不得复用首次结果掩盖调用错误；
- 订单行、库存余额、业务预留、库位级预留分配和库存流水必须在同一数据库事务中完成校验与变更；
- 使用版本字段或数据库行锁阻止并发超卖、超拣和超发；
- 所有动作记录订单、明细、数量、账号、会话、时间、幂等键和请求标识；
- 失败命令可记录操作审计，但不得生成有效库存事实。

## 8. 查询与页面展示

销售订单详情目标返回：

- 持久化字段：`status`、`completion_type`、完成审计字段；
- 派生字段：`fulfillment_status`、每行五个剩余/在途数量；
- 明细事实：`ordered_qty`、`reserved_qty`、`picked_qty`、`shipped_qty`；
- 当前用户可执行的 `allowed_actions`；
- 直接拣货、内部自动预留、异常退回/释放、发货和人工完成的时间线。

页面必须：

- 并列展示生命周期和履约进度；
- 按订单行展示数量进度，不跨不同计量单位直接求和；
- 正常操作区只展示“直接拣货”和“发货”；预留作为直接拣货结果摘要展示，不提供单独的正常预留步骤；
- 退回拣货和释放预留放入异常处理区，并说明适用条件；
- 对人工完成订单显示完成原因，并保留实际已发货数量；
- 人工完成后的主标签显示“已完成（人工）”，不得把未发货数量显示成已经发货，也不得显示“全部发货”；
- 仅在后端允许且当前角色有权限时启用动作；
- 明确提示原型数据与接口均为目标设计，不表示后端已经实现。

## 9. 典型示例

订单行数量为 100：

1. 审核后：`Approved + NotStarted`，数量为 `100 / 0 / 0 / 0`；
2. 直接拣货 40：系统在同一事务内自动预留并拣货 40，数量为 `100 / 40 / 40 / 0`，进度为 `InProgress`；
3. 发货 40：数量为 `100 / 40 / 40 / 40`，本次对应的库存有效预留释放；
4. 再直接拣货 60：系统自动预留并拣货 60，数量为 `100 / 100 / 100 / 40`；
5. 发货 60：数量为 `100 / 100 / 100 / 100`，自动进入 `Completed + FullyShipped + Normal`。

若步骤 3 后终止剩余数量：此时不存在未发货暂存数量，可直接人工完成，最终进入 `Completed + InProgress + Manual`，已发货 40 保持不变。若直接拣货后又决定不发，必须先退回未发货拣货，再由人工完成命令释放退回后留下的有效预留。
