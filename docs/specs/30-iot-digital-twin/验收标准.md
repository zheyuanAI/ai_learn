# IoT 设备接入验收清单

## 验收前提

- 本清单验收一期 IoT 后端实现；设备、凭证、遥测、状态、告警、上下文 Controller、持久化端口和 MQTT 消费端已落地。真实 Broker 联调仍以外部密码/ACL 注入为前提，未注入时保持 fail-closed。
- 一期告警规则已经限定为单指标触发阈值、恢复阈值和告警等级；离线默认 60 秒并允许按设备模型调整。复杂组合算法不进入一期。
- 场景中的失败分支必须返回 `接口契约.md` 定义的对应业务错误码。

## 核心验收

- 能创建 `DeviceProfile`、`Device` 和有效设备凭证，且一期设备协议只能为 MQTT。
- 有历史数据的设备只能停用，不能物理删除；设备凭证明文只在创建时展示一次。
- `DeviceTelemetry`、`DeviceStatus`、`DeviceAlarm` 分别保存原始事实、当前快照和告警生命周期；延迟消息不会倒退当前状态。
- MQTT QoS 1 重复消息按 `device_id + message_id/sequence` 去重，不重复生成遥测、状态变化或告警事实。
- IoT 独立保存设备事实；Core 暂时不可用时，已经接收的遥测和 IoT 内部告警不丢失。
- Device 可关联工作中心或生产区域；Core 的 OperationExecution 可选关联 Device。
- 告警业务上下文允许自动延后补充或人工补充，且补充行为不改写原始设备事实。
- 设备先恢复后确认时保留“已恢复但未确认”状态，人工确认不伪造恢复时间。
- 一期不存在 Modbus TCP、OPC UA、Ditto 或三维数字孪生接入口。

## 页面验收

- 设备页展示：设备编码、设备模型、MQTT 协议、生命周期状态、工作中心、区域、当前在线 / 运行 / 告警状态和最后通信时间。
- 设备详情将原始遥测列表 / 曲线、当前状态快照和告警历史分区展示。
- 凭证管理只展示凭证业务标识与状态，不回显可直接复用的明文凭证。
- 告警详情展示：告警编号、设备、类型、等级、触发时间、确认人、确认时间、恢复时间、上下文状态、可选工序执行与工单。
- 上下文待补充时页面明确标识 `Pending`，授权用户可人工补充，不把空关联展示成已自动关联。

## 场景验收

### 场景 1：设备模型、设备与凭证接入

- 前置：当前租户可管理设备。
- 操作：创建设备模型及允许指标，创建 MQTT Device，配置有效凭证，再用该凭证上报合法消息。
- 结果：消息解析到正确租户和设备，DeviceTelemetry 可查。
- 失败：设备不存在、已禁用或不属于当前租户时返回 `IOT_DEV_001`；非 MQTT 协议返回 `IOT_DEV_002`；无效或撤销凭证返回 `IOT_CRED_001`；未允许指标返回 `IOT_PROFILE_001`。

### 场景 2：Telemetry / Status / Alarm 三类事实分离

- 前置：测试夹具已配置并冻结一条可稳定触发及恢复的告警规则。
- 操作：上报合法遥测，使状态更新并触发告警；确认告警后再上报恢复事实。
- 结果：原始遥测保留；DeviceStatus 仅反映最新快照；DeviceAlarm 保留 `Triggered -> Acked -> Recovered` 生命周期。
- 失败：对非 `Triggered` 告警重复确认返回 `IOT_ALM_001`。

### 场景 3：MQTT QoS 1 重复消息去重

- 前置：Device 与凭证有效。
- 操作：连续两次发送相同 `device_id + message_id` 和相同载荷，再对只含 `sequence` 的消息执行同样测试。
- 结果：第二次均按幂等成功接收，`duplicate = true`；每个消息只生成一组遥测，状态只推进一次，告警不重复生成或恢复。
- 失败：消息同时缺少 `message_id` 和 `sequence` 返回 `IOT_TLM_002`；同一去重键载荷不同返回 `IOT_TLM_003`。

### 场景 4：不同设备不被错误去重

- 前置：两个 Device 均有效。
- 操作：两台设备上报相同 `message_id` 或 `sequence`。
- 结果：两台设备各保存自己的遥测事实，证明去重键包含 `device_id`。

### 场景 5：Core 故障不丢采集事实

- 前置：模拟 Core 不可用，IoT 自身数据库和 MQTT 接入可用。
- 操作：设备上报可触发状态与告警变化的有效消息。
- 结果：DeviceTelemetry、DeviceStatus 和 DeviceAlarm 在 IoT 内可查询；告警业务上下文可为 `Pending`，采集链路不因 Core 调用失败而回滚。
- 恢复：Core 恢复后自动或人工补充业务上下文，原始遥测与告警时间不变。

### 场景 6：设备与生产上下文关联

- 前置：Device 已关联工作中心或区域，Core 中存在可选关联该设备的未完成 OperationExecution。
- 操作：产生告警并执行自动上下文判断；若判断不可用或不可靠，再由授权用户人工补充。
- 结果：告警可关联 `operation_execution_id` 和 `work_order_id`；人工补充时 `context_source = Manual`。
- 失败：不存在、关系不一致或跨租户的业务上下文返回 `IOT_CTX_001` 或 `IOT_TENANT_001`。

### 场景 7：告警确认与恢复

- 前置：告警为 `Triggered`。
- 操作：授权用户确认告警，随后设备上报满足已确认恢复规则的有效事实。
- 结果：告警进入 `Acked` 并记录确认人 / 时间，再进入 `Recovered` 并记录恢复时间。
- 边界：确认接口不伪造恢复，业务上下文补充不改变告警生命周期时间。

### 场景 8：设备先恢复后确认
- 前置：告警为 `Triggered`
- 操作：设备先上报满足恢复阈值的数据，之后授权用户补充确认
- 结果：先进入 `RecoveredUnacked` 并保存真实恢复时间，再确认进入 `Recovered`；确认时间不覆盖恢复时间

### 场景 9：延迟与非法消息
- 操作：先上报新状态，再上报时间更早的合法消息；随后上报包含一个非法指标的多指标消息
- 结果：延迟消息作为原始遥测保存但当前状态不倒退；非法多指标消息整条拒绝，不保存部分指标

## 自动化测试

- DeviceProfile 允许 / 拒绝指标校验。
- MQTT Device 创建成功，Modbus TCP 与 OPC UA 返回 `IOT_DEV_002`。
- 有效、撤销、跨设备和跨租户凭证校验。
- 遥测格式校验及缺少消息标识返回 `IOT_TLM_001` / `IOT_TLM_002`。
- `device_id + message_id` 与 `device_id + sequence` 两种去重路径。
- 相同去重键相同载荷幂等成功，不重复产生 Telemetry / Status / Alarm；不同载荷返回 `IOT_TLM_003`。
- 两台设备使用相同消息标识时分别保存。
- Telemetry 保存失败时不得推进 DeviceStatus 或生成 DeviceAlarm。
- Core 不可用时 IoT 事实仍保存，上下文保持待补充。
- 告警合法确认 / 恢复路径通过，非法重复操作返回 `IOT_ALM_001`。
- 自动上下文缺失可人工补充，跨租户补充返回 `IOT_TENANT_001`。
- 跨租户设备、遥测、状态和告警查询返回空数据。

## 一期范围否定验收

- API、MQTT Topic、页面和测试中不出现 Modbus TCP 或 OPC UA 接入实现。
- 不存在 Eclipse Ditto Thing/Feature 映射或同步接口。
- 不存在三维数字孪生、Cesium 或通用多协议适配流程。
