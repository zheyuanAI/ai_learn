# 一个月交付与文档目录迁移设计

**日期：** 2026-08-20  
**状态：** 已确认（用户于 2026-08-20 确认）  
**适用工程：** `ai_learn_developProject`

## 1. 决策结论

本项目的正式开发周期调整为一个月，采用四周纵向业务切片推进。原十周计划仅代表前期学习安排，保留为历史学习资料，不再作为当前项目的开发排期或交付承诺。

一个月交付目标为“一期黄金业务闭环可运行、可演示、可验收”：覆盖 ERP/WMS、MES、IoT 主链路；GIS、经营看板与 AI 助手只实现支撑闭环的轻量只读能力。数字孪生仿真、知识库训练及其他扩展能力归入二期，不进入本月强制范围。

现有 `openspec/` 目录整体迁移至 `docs/openspec/`，现有 `specs/` 目录整体迁移至 `docs/specs/`。迁移统一文档入口，并在不改变业务代码、构建和运行约定的前提下优先使用中文文件名；OpenSpec CLI 以 `ai_learn_developProject/docs/` 作为受支持工作目录，并已在那里验证工件识别，迁移不改变 OpenSpec 的显式触发规则，也不改变领域规格的事实源地位。

## 2. 一期完成标准

本月完成不是指页面数量或接口数量达到某个数字，而是以下结果同时成立：

1. 黄金业务闭环能够从销售需求开始，经过供需关联、采购入库、生产执行、成品入库，最终完成销售发货。
2. 库存预占、库存移位、领退料和发货扣减遵守统一库存规则，关键状态变化有依据、可查询。
3. 前端、后端与 PostgreSQL、Redis、Mosquitto 的必要链路能够联通；中间件未启动时仍保留既定健康检查与静态原型回退说明。
4. MES 工序执行能够关联销售订单行和设备上下文；IoT 遥测、状态、告警分离，并具备消息去重语义。
5. 跨域追溯能够从销售订单行查询到工单、物料移动、工序执行和设备事实。
6. 二维地图、经营看板和 AI 助手只读取已经存在的业务事实，不创建第二套业务状态，不代替核心业务决策。
7. 核心正常流程、关键异常流程、构建检查和演示脚本均完成验证，并保留可复现的验收步骤。

## 3. 四周交付切片

### 第 1 周：工程底座与库存内核

- 固化 Java 21、Maven 3.9.1、Node 20 和既定服务端口基线。
- 建立最小认证与租户边界、必要主数据。
- 实现库存台账、库存余额和位置语义，先确定库存不变量。
- 交付能够独立验证的库存增减、移位和查询链路。

### 第 2 周：采购入库与销售出库

- 实现采购收货进入 `ReceivingStaging`、上架通过库存移位完成。
- 实现销售库存预占、拣货进入 `ShippingStaging`、发货时扣减总库存。
- 保留人工供需关联，避免在一期引入自动 MRP 或复杂分配算法。
- 交付 ERP/WMS 范围内可运行的入库与出库闭环。

### 第 3 周：制造执行与 IoT 设备事实

- 销售订单行关联工单，完成生产领料、退料、工序执行和成品入库。
- 工序执行覆盖开始、暂停、恢复和完成等必要状态。
- 通过 Mosquitto 接入设备遥测、设备状态和告警；按 `message_id`、`sequence` 执行去重语义。
- 将设备事实关联至 `operation_execution_id`，但不让设备消息直接改写库存或生产业务状态。

### 第 4 周：追溯、轻量智能与验收

- 完成销售订单行到工单、库存移动、工序和设备事实的跨域追溯。
- 完成二维地图、经营看板和 AI 只读查询的轻量实现。
- 验证正常流程、重复消息、非法状态迁移、库存不足和中间件异常等场景。
- 完成端到端联调、部署说明、验收记录和演示脚本。

## 4. 执行方式

采用纵向业务切片，每周都形成可运行、可验证的增量。每个切片按“领域规则与验收标准 → 数据模型与接口 → 后端实现 → 前端交互 → 自动化验证 → 人工演示”的顺序闭环，不把跨域联调集中到最后一周。

若进度出现偏差，范围收缩顺序固定为：先减少二期展示与智能增强，再简化非核心交互，最后调整非关键管理功能。库存内核、黄金业务闭环、状态一致性和可追溯性不得作为赶工牺牲项。

## 5. 规格与 OpenSpec 迁移设计

### 5.1 目录结果

迁移前：

```text
ai_learn_developProject/openspec/
ai_learn_developProject/specs/
```

迁移后：

```text
ai_learn_developProject/docs/openspec/
ai_learn_developProject/docs/specs/
```

OpenSpec 内的 `README.md`、`config.yaml`、`guides/`、`schemas/`、内部 `specs/` 以及已有 `changes/`（若存在）保持相对层级不变。领域规格原有的 `00-project`、`10-erp-wms`、`20-mes`、`30-iot-digital-twin`、`40-gis-dashboard`、`50-ai-assistant` 目录名保持不变，避免破坏稳定的领域编号和技术标识。

### 5.2 路由规则

- 普通任务仍不自动进入 OpenSpec。
- 只有用户请求明确以 `OpenSpec` 或 `openspec` 开头时，才读取 `docs/openspec/README.md` 并执行其流程。
- `docs/specs/` 是长期领域规格事实源；`docs/openspec/` 承载变更工件与协作流程，二者职责不合并。

### 5.3 联动修改范围

迁移时必须同步更新：

- `AGENTS.md` 与 `CLAUDE.md` 的事实源优先级、入口、目录说明和联动检查规则；
- 项目根 `README.md`、`docs/README.md`、`docs/项目目录结构.md`；
- `docs/rules/AGENTS_General.md` 中属于当前仓库实际入口的路径说明；
- `docs/openspec/**` 内引用原根目录 `openspec/...` 的执行路径；
- 原型、前端说明及其他当前生效文档中指向 `specs/**`、`openspec/README.md` 或 `openspec/**` 的链接。

历史审查快照、历史差异文件、编译产物和参考工程中的文本不做机械改写；它们不作为当前入口。

## 6. 文档更新范围

正式计划与项目概览统一使用“一个月/四周”开发周期。原十周资料按以下原则处理：

- 文件可以保留原名称，以免破坏历史引用；
- 文档开头增加“历史学习计划/已停止作为开发排期”的醒目标识；
- 当前 README 和文档导航不再称其为“当前生效总计划”；
- 正式开发计划统一指向 `docs/specs/00-project/正式项目计划.md`；
- 已明确标为历史记录、审查快照或旧计划的内容保留原始时间表，不伪装成当前事实。

### 6.1 中文文件名边界

业务和项目说明文档优先使用中文文件名。领域目录编号、代码目录、配置文件、构建文件以及会被工具按固定名称识别的文件保持原名。

领域规格文件统一按下表迁移：

| 原文件名 | 中文文件名 |
| --- | --- |
| `overview.md` | `概述.md` |
| `domain.md` | `领域模型.md` |
| `api.md` | `接口契约.md` |
| `acceptance.md` | `验收标准.md` |

项目级规格单独使用更明确的名称：

| 原文件 | 迁移后文件 |
| --- | --- |
| `specs/00-project/overview.md` | `docs/specs/00-project/项目概述.md` |
| `specs/00-project/architecture.md` | `docs/specs/00-project/架构设计.md` |
| `specs/00-project/project-plan.md` | `docs/specs/00-project/正式项目计划.md` |
| `specs/00-project/prototype.md` | `docs/specs/00-project/原型与交互说明.md` |

以下名称保持不变：

- `README.md`、`AGENTS.md`、`CLAUDE.md`、`CONTEXT.md`；
- `pom.xml`、`package.json`、`application.yml`、`docker-compose.yml` 等代码、构建和运行文件；
- `docs/openspec/` 内 `config.yaml`、`schema.yaml`、模板文件名和命令约定路径；
- `docs/superpowers/` 中受工作流命名规范约束的历史计划和审查工件；
- Java、TypeScript、Vue、HTML、PowerShell 等源代码和运行脚本。

`docs/project-structure.md` 迁移为 `docs/项目目录结构.md`，`docs/plans/10_week_project_plan.md` 迁移为 `docs/plans/十周学习计划-历史.md`。其他纯说明性文档只有在当前引用链能够完整同步时才改为中文名，避免为追求中文命名破坏工具入口或历史追溯。

## 7. 验证策略

文档和目录调整完成后执行以下检查：

1. 搜索当前生效文件，确认不存在把十周描述为当前交付周期的表述。
2. 搜索当前生效文件，确认领域规格入口全部指向 `docs/specs/`，OpenSpec 入口全部指向 `docs/openspec/README.md`。
3. 检查 `docs/specs/` 和 `docs/openspec/` 目录结构完整，原根目录 `specs/`、`openspec/` 不再作为有效入口。
4. 检查中文文件名、Markdown 相对链接和 OpenSpec 模板/指南内的路径一致性。
5. 检查仍保留英文名称的文件均属于工具约定、代码、构建、运行或历史工作流工件，不对它们做机械改名。
6. 因前端路由、构建配置和后端代码不在本次新增变更范围，不以本次文档迁移为由修改业务代码；若现有未提交改动已经影响前端，则保留其既有构建验证结果并避免无关重写。

## 8. 非目标

本次调整不代表立即实现一个月计划中的全部业务代码，也不新增数据库 Schema、Controller、鉴权机制或消息算法。它先统一交付周期、范围边界和协作入口；后续实现必须继续以正式规格、接口契约和验收标准为依据。

本次不执行 Git 提交，由用户审核工作区改动后自行决定提交时机。
