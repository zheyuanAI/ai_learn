# 销售订单分批履约与高保真原型设计

## 设计目标

在不引入状态组合爆炸的前提下，准确表达一个销售订单同时存在部分预留、部分拣货和部分发货，并将冻结后的业务规则转化为可点击、可评审的高保真销售交付原型。

## 方案比较与结论

### 方案一：扩充单一状态枚举

增加 `PartiallyReserved`、`PartiallyPicked`、`PartiallyShipped` 等状态。优点是列表标签直观，缺点是无法表达多个履约阶段并存，组合数量会快速增长，且容易把展示状态误作命令前置条件。

### 方案二：只保留一个 `Fulfilling`

生命周期使用 `Draft / Submitted / Approved / Fulfilling / Completed`，数量负责具体进度。优点是简单，缺点是 `Approved` 与 `Fulfilling` 的切换仍由派生数量驱动，会把流程控制和展示进度重新耦合。

### 方案三：生命周期与履约进度双轴（采用）

持久化 `status = Draft / Submitted / Approved / Completed`；查询时由订单行数量派生 `fulfillment_status = NotStarted / InProgress / FullyShipped`。仓储动作不改变生命周期，所有权限判断只使用生命周期、角色和数量条件。

此方案保持状态机最小，数量是履约事实源，且允许页面同时表达“已人工完成但只发出一部分”等真实组合。

## 领域设计

正式规则写入 `docs/specs/10-erp-wms/销售订单业务规则.md`。关键设计为：

- 订单行满足 `0 <= shipped_qty <= picked_qty <= reserved_qty <= ordered_qty`；
- `reserved_qty` 表示仍有效预留或已进入下游的数量，`picked_qty` 表示仍在发货暂存位或已经发货的数量；
- 库位级预留由 `InventoryReservationAllocation` 表达，拣货/退回同步迁移实物和有效预留分配；
- 发货释放库存预留，但不回退订单行履约里程碑；
- 人工完成前必须退回未发货拣货，随后释放剩余有效预留；
- 正常全部发货和人工终止都进入 `Completed`，通过 `completion_type` 区分。

## 高保真原型设计

目标页面为 `docs/prototype/pages/sales-outbound.html`。页面采用“订单列表 + 订单工作区”的桌面操作台结构：

- 顶部提供订单检索、生命周期/履约组合筛选和角色切换；
- 左侧订单队列展示客户、计划发货日、两个状态轴和异常提醒；
- 右侧详情同时展示订单状态、完成方式、各行数量进度和库存位置；
- 履约管线按预留、拣货、发货三个阶段并列呈现，不用单一阶段标签覆盖并行进度；
- 操作区根据销售人员/仓库人员和当前状态切换可用按钮；
- 预留、拣货、退回、发货与人工完成使用抽屉/对话框演示输入、校验和结果；
- 场景切换允许评审“部分履约”“人工完成”“正常完成”三种组合；
- 时间线保留幂等键、账号、会话和库存影响摘要。

## 交互与错误反馈

- 禁用动作展示明确原因，不只改变颜色；
- 数量输入超过可操作上限时就地提示；
- 人工完成存在未发货暂存数量时阻止提交，并引导先执行退回；
- 成功操作通过页面内状态和时间线同步反馈；
- 所有操作仅修改浏览器内假数据，并持续标注“目标设计，接口未实现”。

## 验证范围

- 桌面宽度下列表、详情、操作区无重叠；
- 约 768px 宽度下可顺序阅读和操作；
- 三个示例场景的双轴状态、数量不变量和按钮权限一致；
- 页面不再出现将 `Reserved / Picking / Shipped` 当作销售订单主状态的描述；
- 原型 README、流程工作台和正式规格中的状态口径一致。
