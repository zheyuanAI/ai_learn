# 阶段 0-1 修复设计

> 日期：2026-09-03
>
> 状态：已废止，仅作为 2026-09-03 早期设计追溯记录；不代表当前方案或阶段验收结论，当前数据库基线与验收口径以 `docs/specs/00-project/架构设计.md`、`认证与后台管理验收标准.md` 为准。

## 目标与固定边界

本轮修复 V5 菜单租户隔离迁移、Auth 菜单管理 CRUD/状态、角色与菜单授权前置校验、Flyway 历史表接管、测试隔离和阶段 0 文档漂移。所有服务继续使用同一个 PostgreSQL 实例、同一个 `public` schema；只支持当前租户管理员，不增加平台超级管理员；优先业务完整性，不扩展安全加固；不修改已经执行过的 V1-V4，也不操作当前开发数据库。

## 方案

### 数据库迁移

V5 按以下顺序执行：

1. 先删除 V1 创建的全局 `uq_auth_menu_code_active`，避免向第二租户插入同编码菜单时先触发全局唯一冲突。
2. 确保既有 V2 默认租户 `a0000000-0000-0000-0000-000000000001` 存在；仅按 ID 幂等补齐真实租户 B，不创建或使用 `10000000-...` 替代默认租户。
3. 增加 `tenant_id`、`visible`、`status` 临时可空/带默认字段；将所有历史菜单回填到 `a000...0001`，只修复必要的历史组件路径。
4. 插入租户 B 的全量演示菜单副本，并保证 B 的管理员角色、角色菜单关联和菜单记录都使用 B 的 UUID。
5. 回填完成后为 `visible`、`status` 设置明确默认值和合法值 `CHECK`，为 `tenant_id` 设置 `NOT NULL` 和租户外键，创建 `(tenant_id, menu_code) WHERE isdel = 0` 部分唯一索引及租户检索索引。

应用配置统一使用 `auth_flyway_schema_history`。对于已执行 V1-V4 的旧数据库，文档与可执行接管 SQL 采用“先在同一事务中复制旧历史表结构/记录，再切换应用配置”的方式：新历史表必须完整保留既有 Auth 迁移的 `installed_rank/version/description/type/script/checksum/installed_by/installed_on/execution_time/success` 记录，复制前检查源表存在、Auth 版本记录唯一且成功，复制后校验行数和版本集合一致；确认接管后才启动新配置执行 V5。若共享表包含其他模块记录，只复制 `V1`-`V4` 的 Auth 记录，并要求先确认这些记录确实属于 Auth 迁移；不删除旧共享表。

### 后端菜单与授权

菜单管理服务始终从 `TenantContextHolder` 取得租户，并对菜单详情、树、创建、更新、删除和状态变更按当前租户/未删除过滤。`MenuUpdateRequest` 增加必填 `menuCode`，更新时检查租户内未删除编码唯一性并真实持久化；`MenuStatusUpdateRequest` 改为接收 `status`，`PUT .../status` 只更新 `ACTIVE`/`DISABLED`，普通更新继续处理 `visible`。管理 VO、登录菜单 VO 和前端 `MenuItem` 均返回 `status`。

用户分配角色和角色分配菜单均在任何关系删除前，通过一次批量查询校验全部 ID：数量、租户归属、`isdel = 0`、目标状态 `ACTIVE`。空列表允许清空关系；重复 ID 先去重或按请求语义拒绝，不能产生重复关系。任何一个 ID 非法都抛出业务校验错误，事务不发生关联删除或部分插入。创建/更新角色、创建/更新用户的初始关联也复用同一批量校验。

### 测试与验证

现有快速测试继续使用 H2，但改为真实租户 ID 与菜单/角色关联数据，并让测试上下文使用内存 `SessionCacheService`，不连接开发 Redis。真实迁移测试必须与 H2 快速回归分开，使用隔离 PostgreSQL 12.1 临时数据库/容器或等价隔离实例执行真实 Flyway SQL，分别覆盖全新库 V1→V5 与已有 V1-V4 库升级 V5；测试断言租户 ID、索引、约束、历史菜单回读、同编码跨租户、`tenant_id NOT NULL` 和历史管理员菜单可见。

管理集成测试补充：菜单编码修改回读、`visible` 与 `status` 独立生效、真实租户 B 的跨租户拒绝、停用角色/菜单的整体拒绝，以及失败前后原关联集合不变。

## 取舍

- 不改 V1-V4，避免破坏已经执行的历史；V5 同时兼容全新库和当前 V1-V4 状态。
- 不把菜单状态合并为一个字段，保留 `visible`（导航展示）与 `status`（业务启用）的独立语义。
- 不把 Flyway 历史表迁移伪装成新的 baseline，也不自动清理旧共享表；通过显式复制和校验降低误执行 V1-V4 的风险。
- 不把数据库迁移验证伪装成正则测试；静态检查只保留为辅助，真实 PostgreSQL 执行结果作为迁移证据。

## 验收证据

最终仅在以下证据实际取得后报告结果：`mvn clean test`、`mvn clean package`、`npm run build`、两条 PostgreSQL 12.1 迁移路径、连续两次后端测试、`git diff --check`。如任一项缺失，明确标注“未完成”，且确认未提交 Git、未修改 V1-V4、未操作当前开发数据库。
