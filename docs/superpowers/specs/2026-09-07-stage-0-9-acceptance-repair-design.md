# 阶段 0–9 验收返工设计

> 日期：2026-09-07  
> 状态：待用户评审  
> 执行对象：本任务执行 AI  
> 事实基线：`0ba119c` 及其后的当前未提交工作树  
> 上游计划：`docs/superpowers/plans/2026-09-07-stage-0-7-ui-repair-plan.md`

## 1. 目标

本次返工不再按“页面能打开”或“构建成功”判断完成，而是修正阶段 0–9 验收中发现的真实性、权限、幂等、业务关联和自动化验收缺陷，并最终用真实服务、真实角色和可核对数量跑通一期黄金业务闭环。

返工分为两个阶段：

1. **缺陷止血**：先消除默认放行、占位或随机业务 ID、错误信息丢失、错误菜单迁移、陈旧数据冒充实时、E2E 假绿色等基础缺陷。
2. **业务闭环**：再按采购、销售、MES、IoT/看板、黄金闭环的依赖顺序补齐第 5–9 批，逐批形成可复现证据。

本设计不扩大一期范围，不引入 MRP、APS、RabbitMQ、MinIO、pgvector、三维数字孪生、RAG、WIP、线边仓或复杂返工流程。

## 2. 执行原则

### 2.1 单批领取与停止闸门

- 执行 AI 每次只能领取一个返工批次，不能预先修改后续批次文件。
- 每批开始前必须保存基线、复现失败并列出预计修改文件；未复现不得修改。
- 每批结束后必须运行本批测试、相关模块回归及 `git diff --check`，用户验收后才能进入下一批。
- 发现现有接口、权限点、状态机或字段契约无法支撑页面闭环时，立即停止并报告，不得自行发明接口、UUID、状态或业务规则。
- 构建通过、测试被跳过、只列出测试、HTTP simulate、页面显示成功或健康检查正常，都不能代替对应业务闸门。

### 2.2 Git 与工作树纪律

- 禁止执行 `git commit`、`git add`、`git reset --hard`、`git checkout --`、全仓格式化或批量替换。
- 开始每批前记录 `git status --short`、`git diff --stat` 和本批基线 commit。
- 当前未提交改动视为用户资产。若本批需要修改同一文件，必须先说明重叠位置和兼容方案。
- 每批只提供建议提交清单和建议提交信息，由用户决定是否提交。
- Playwright 快照、测试结果、构建产物、日志、凭据和临时数据不得加入版本控制。

### 2.3 核心业务所有权

以下内容默认由用户主导实现：

- 登录、JWT、租户上下文、权限菜单；
- 库存预留、移动、扣减、回补；
- 收货、质量处置、上架、直接拣货、发货、领退料、成品入库等关键状态流转；
- 幂等、租户隔离和库存一致性。

执行 AI 可以完成诊断、测试、DTO、查询投影、前端接入和非核心配套代码。若修复需要改变上述核心规则、接口字段、权限点、错误码或状态机，必须先形成差异说明，等待用户明确授权。

## 3. 统一事实与安全约束

### 3.1 事实来源

判断“已实现”时按以下顺序取证：

1. `frontend/`、`backend/`、`deploy/` 的实际代码与运行配置；
2. Maven、npm 依赖与构建配置；
3. 项目级和领域级正式规格；
4. 原型及交互说明；
5. 实施计划和历史交接记录。

文档声明不能覆盖代码事实。找不到真实接口或数据源时必须写“未在仓库中确认”，不能用占位对象让页面暂时可选。

### 3.2 角色与权限

- 一期固定六类角色：租户管理员、销售、采购、仓库、生产质检、IoT。
- 租户管理员不自动拥有业务操作权限。
- 后端权限和对象状态是最终裁决；前端按钮仅反映后端能力。
- 契约承诺返回 `allowedActions` 时，字段缺失、集合为空、动作未知或 `enabled=false` 均拒绝操作。
- 尚未返回动作表的只读事实端点不能机械改成全部禁用，应使用正式读权限和事实冻结状态展示，并由后端继续校验写操作。
- 禁止测试使用临时全权限角色或跨岗位硬编码人员绕过权限。

### 3.3 错误与请求号

前端统一错误对象必须保留：

- HTTP 状态码；
- 业务 `code`；
- 响应体 `request_id`；
- 可理解的 `message`；
- 网络超时、结果不确定和服务端明确拒绝之间的区别。

页面至少区分 401、403、404、409、422、503 和网络超时。禁止只写 `console.warn/error` 后继续流程，禁止把错误数据渲染成成功、零值或“实时”。

### 3.4 命令幂等

- 一个用户业务命令创建一次 `Idempotency-Key`。
- 执行中禁双击；网络超时或结果不确定时复用同一键。
- 重试前优先复读事实，禁止自动换键重复收货、库存移动、拣货、发货、领料或入库。
- 明确开始一笔新业务操作时才能创建新键。
- 幂等封装必须接入实际命令调用点；只有未使用的 composable 不算完成。

## 4. 两阶段返工结构

### 阶段 A：缺陷止血

#### A0：重新建立可信验收基线

目标：区分代码缺陷、环境缺陷和未完成能力，确保所有后续结果可重复。

- 固定 Java 21、Maven 3.9.1、Node 20、PostgreSQL 12.1、Gateway 20001、Auth/Core/IoT 10002–10004。
- 记录三个 Flyway history 的最新版本和 success 状态，但不执行清库或自动迁移。
- 修正演示账号名称，凭据只通过环境变量或受保护 storage state 注入。
- 安装或确认 Playwright Chromium 后实际执行用例，不能只运行 `--list`。
- 菜单、七卡、无权限按钮三个断言必须在同一启动方式和同一数据基线下重复两次得到相同结果。
- 纠正文档中的冲突完成声明；未验证项明确标记为未验证。

停止条件：服务版本、数据库版本、登录角色或测试浏览器不确定时不得进入 A1。

#### A1：权限、错误和幂等止血

目标：消除假按钮、错误信息丢失和重复业务命令风险。

- 修正 `actionGuard` 的缺失动作默认放行。
- 核对响应体 snake_case `request_id` 与响应 Header，形成统一 `ApiError`。
- 将 `useCommand` 接入真实写命令；优先选择一个低风险命令验证同键重放，再推广到本次涉及的关键命令。
- 无读权限展示独立无权限态；无写权限隐藏或禁用按钮并展示原因。
- 使用正式六角色和第二租户验证权限及租户隔离。

停止条件：若后端未提供页面所需动作能力或权限点，先报告契约缺口，不得前端推断放行。

#### A2：菜单、路由和迁移止血

目标：确保菜单、正式路由、旧链接、详情直达和 404 行为一致。

- 从真实 `/api/me/menus` 枚举全部可见叶节点，不硬编码单个菜单作为全量证明。
- 旧路由只 redirect 到正式页面，保留业务 ID、查询参数和返回位置。
- Auth V8 只修正系统种子且仍为已知旧路径的记录，不覆盖租户自定义路径。
- 采购、销售、调拨详情验证列表进入、直链、刷新、浏览器后退和资源不存在。
- 未知路径展示 404，无权限展示 403，不允许静默返回首页。

停止条件：迁移无法可靠区分系统种子与租户自定义记录时，不修改迁移，先提交数据识别方案供用户确认。

#### A3：看板与陈旧数据止血

目标：看板和 GIS 只展示真实投影，不把错误、旧缓存或缺源显示为实时数据。

- 七个 Dashboard 端点必须经 Gateway 验证权限、合法查询和非法查询。
- 成功且明确 fresh 才显示“实时”。
- 有旧结果时保留原值、原 `generated_at/source_updated_at`，展示 `stale=true` 和 `stale_since`。
- 无旧结果时显示不可用及请求号，不生成零值。
- 同步验证 site-maps、traceability、exception-center 的已注册、权限和源故障行为。
- IDEA 组合启动停止并重启一次，确认不依赖临时 shell 环境变量。

停止条件：缺少 Core↔IoT HMAC 或必要 Facts 端口时，不取消条件装配、不填充假数据，按运行配置缺口处理。

#### A4：真实目录与选择器止血

目标：任何业务表单都不要求用户猜 UUID，也不使用占位人员或固定前 200 条数据。

- 仓库、UOM、产品、库位、客户、供应商使用真实目录。
- 工单、冻结工艺工序、工作中心、同租户操作员和设备使用受控查询。
- 普通生产角色不得为了读取人员选项获得用户管理权限；若缺少受控人员目录，先设计最小只读契约并等待用户确认。
- 选择器支持服务端搜索或分页；改变上游选项时清除失效下游值。
- 选项展示编码和名称，提交真实 ID；停用或跨租户对象不可选且后端仍需拒绝。

停止条件：真实目录未在仓库中确认时，页面显示明确不可用，不得保留硬编码或随机 ID。

### 阶段 B：业务闭环

#### B1：采购入库闭环

按“采购创建与审核→外观验收→实际接收→采购到货质检→处置决定→仓库执行→上架”完成。

- `PurchaseReceipt.id`、订单行 ID、收货行 ID、质检 ID、处置 ID 和上架任务 ID 必须来自实际接口返回，互不代用。收货推荐入口由服务端按可信租户与 `Idempotency-Key` 分配并返回独立 `receiptId`，客户端不能生成随机 ID。
- `arrived = rejected + received`；拒收不入库存且仍计待收。
- 实际接收仅增加一次库存并全部进入 QualityHold。
- 质检不改变库存；放行移动到 ReceivingStaging；报废或退回只扣实际确认数量；上架只移动位置。
- 每次写操作成功后复读采购详情、质量事实、库存余额和库存流水。
- 完成订单的存量收货仍可继续质检和上架；人工完成不补造事实。

数量闸门：以原料 R 到货 3、拒收 1、实收 2 为统一样本，最终企业实物 R 增加 2。

#### B2：销售履约闭环

按“销售创建与审核→直接拣货→分批发货→完成”完成。

- `/sales/picks` 使用真实分页订单驱动队列，不显示不存在的任务号。
- 直接拣货复用既有销售履约命令，不复制库存逻辑。
- 来源库位按商品、仓库、批次和可用量选择；目标必须是同仓真实 ShippingStaging。
- 直接拣货在同一事务自动预留并移位，不减少企业总实物；发货才减少实物并释放对应预留。
- 支持部分拣货、两次分批发货和未发货拣货退回。
- `fulfillmentOperationId`、salesOrderId 和 salesOrderLineId 不得混用。拣货、退回和发货推荐入口由服务端按可信租户与 `Idempotency-Key` 分配并返回 `operationId`，客户端不能生成或要求人工粘贴业务 UUID。

数量闸门：成品 F 入库 2 后直接拣货 2，先发 1 再发 1；最终 `on_hand=0,reserved=0,available=0`。

#### B3：MES 执行闭环

按“工单→领料→派工→工序执行→报工→生产质检→成品入库”完成。

- 工单来源销售行、BOM 和 Routing 使用真实 ID；审核下达后冻结版本。
- 派工工序来自冻结 Routing，人员来自同租户受控目录，设备来自真实 IoT 目录且允许为空。
- 前置工序未完成时不能开始后续工序；状态按后端 `allowedActions` 控制。
- 领退料使用真实工单、BOM 和库存维度；库存变化只由仓库确认并通过库存应用服务。
- 报工使用真实 OperationExecution，`reportQty=qualifiedQty+defectQty` 且累计不超派工/计划。
- 生产质检使用真实 workReportId 和返回的 inspectionId；Failed 未关闭时阻止非法入库。
- 成品入库只使用累计已检验合格且尚未入库数量，确认后复读库存和工单全量事实。

数量闸门：领用原料 R 2，报工合格 F 2，质检 Passed，成品入库 F 2；不建立 WIP 或线边仓。

#### B4：IoT、追溯、GIS 和看板闭环

- 使用真实 Mosquitto、外部 ACL 和 QoS 1 发布遥测，HTTP simulate 仅作为开发辅助证据。
- 同设备同消息键同载荷重复投递只生成一次遥测、状态推进和告警；异载荷同键必须冲突。
- Core 不可用时，IoT 遥测、状态和告警仍保存，上下文保持 Pending/Retry。
- 告警触发、确认、恢复和生产上下文使用真实时间线与真实业务 ID。
- 追溯能从销售、采购、工单、库存流水或告警进行正反向查询，并明确 `missing_sources/truncated`。
- GIS 点位保存百分比坐标，刷新和调整视窗不漂移；跳转仍经过路由与权限校验。
- Dashboard、地图和追溯对同一事实的状态、数量和时间口径一致。

停止条件：真实 Broker ACL、HMAC 或生产区域 Facts 未确认时，明确记录环境或能力缺口，不宣称通过。

#### B5：黄金闭环和交接

- Golden Flow 必须实际创建并读取真实业务事实，不允许只导航页面或探测按钮。
- 必需按钮、接口或业务 ID 缺失时测试立即失败；禁止 `console.warn` 后继续。
- 使用正式演示账号名称，密码只由环境变量或 storage state 注入。
- 正向链覆盖基础数据、销售、工单、采购、入库、生产、IoT、成品入库、销售发货和全域追溯。
- 负向链覆盖 403、跨租户隔离、同键幂等、库存不足、非法状态迁移和源服务不可用。
- 同一清洁业务样本连续执行两次；第二次使用新业务编号但相同固定数量，避免依赖第一次残留数据。
- 文档只把实际完成且可复现的项目标成通过；环境阻塞和未确认事实单独列出。

## 5. 测试与证据模型

### 5.1 每批最小验证

每批至少提供：

1. 修改前失败命令、退出码和关键错误；
2. 修改后同一命令的通过结果；
3. 受影响模块单元或接口测试；
4. `npm run build` 或对应 Maven 模块测试；
5. `git diff --check`；
6. 真实浏览器路径、角色、最终 URL、关键请求状态和页面截图；
7. 修改文件清单、未验证项和剩余风险。

### 5.2 后端验证边界

- 必须使用仓库 Java 21 和 Maven 3.9.1。
- Core、IoT、Gateway 分模块测试必须通过。
- Auth PostgreSQL 迁移测试依赖隔离数据库时，应启动文档化隔离实例或明确记录环境阻塞；不能把未运行写成通过。
- 修改核心状态、库存、权限、租户或幂等时必须补自动化回归。

### 5.3 浏览器证据等级

- A：真实角色、真实 Gateway、真实 PostgreSQL/Redis/Mosquitto 完成读写并复读事实。
- B：真实角色与服务完成只读或局部流程，但没有完整数量对账。
- C：仅代码、单元测试、构建、HTTP simulate 或环境诊断。

P0/P1 关闭必须至少有 A 级证据；环境限制导致只能达到 B/C 时保持未通过。

禁止把临时执行日志写成长期事实，禁止保留相互冲突的“已全部通过”声明。

## 8. 总体验收标准

只有同时满足以下条件，阶段 0–9 才能标记完成：

- A0–A4 和 B1–B5 全部独立验收通过；
- 不存在占位 UUID、随机业务关联 ID、硬编码演示密码、全权限测试角色或静默跳过；
- 全部写操作使用真实返回 ID、正式权限、状态闸门和幂等键；
- 采购、生产、销售三个库存变化链的余额、预留、位置和流水数量一致；
- MQTT QoS 1、告警生命周期、上下文补链和 Core 故障边界有真实 Broker 证据；
- Dashboard、GIS、追溯不建立第二套事实，不以零值或旧缓存冒充实时；
- Golden Flow 和关键负向用例实际执行通过，不只完成编译或用例发现；
- 所有文档声明与当前代码、配置和验证结果一致；
- 工作树改动范围清晰、无生成物、无直接提交，最终由用户决定集成方式。

## 9. 明确不接受的完成方式

- `npm run build` 通过即宣称业务完成；
- `playwright test --list` 通过即宣称 E2E 完成；
- 缺少按钮或数据时 `console.warn` 后继续；
- 使用 `crypto.randomUUID()`、固定 UUID、订单行 ID 代替收货行 ID；
- 固定读取前 200 条并把后续记录视为不存在；
- 取消后端鉴权、条件装配、事务、幂等或租户过滤以换取页面成功；
- 使用 HTTP simulate 代替真实 MQTT 验收；
- 用健康检查代替领域端点和数量对账；
- 修改计划外核心业务或一次提交多个未独立验证批次。
