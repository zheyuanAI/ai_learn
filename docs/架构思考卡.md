# 架构思考卡

> 用途：在推进一个架构点或功能点时，由 AI 先解释问题与约束，使用者作出架构判断，AI 再进行评审。  
> 建议用时：普通功能点 5～15 分钟；出现高风险触发条件时再深入讨论。

## 1. 核心原则

这张卡训练的是架构决策能力，不是让 AI 替使用者选择方案。

一次只讨论一个边界明确的问题，并遵守以下原则：

1. **先解释，后判断**：AI 先解释背景、概念、约束和常见方案，使用者再作选择。
2. **先判断，后评审**：使用者完成判断前，AI 不提前公布自己的推荐答案。
3. **事实与假设分离**：所有重要信息都应归入“事实、假设、未知”之一。
4. **一次只问一个问题**：AI 每轮只提出当前最关键的问题，根据回答继续追问。
5. **按需深入**：不机械遍历全部检查项，只处理会影响当前决策的维度。
6. **说明代价**：任何方案都有适用条件和代价，不以技术名词多少评价架构优劣。
7. **留下验证方法**：结论必须能够通过代码、测试、数据或运行指标验证。

## 2. 适用范围

适合讨论：

- 一个功能应该放在哪个模块；
- 一份数据由谁拥有和修改；
- 一个业务对象应该有哪些状态；
- 某个操作应该同步还是异步；
- 是否需要事务、幂等、并发控制或补偿；
- 是否应该引入缓存、消息队列、独立服务或新组件；
- 当前设计是否存在过度设计或难以演进的问题。

不替代：

- 项目需求和业务规格；
- 代码评审、安全评审和测试；
- 压力测试、故障演练和生产数据验证；
- 需要由业务负责人、技术负责人或合规人员作出的正式批准。

## 3. 标准对话流程

### 阶段一：确定本轮问题

使用者先用一句话说明准备推进的架构点或功能点。

```markdown
功能点：
我现在需要决定：
已有上下文或相关文件：
```

AI 随后整理：

```markdown
本轮决策：只描述一个需要作出的决定

事实：已经由需求、代码、配置、数据或负责人确认的信息
- 

假设：当前暂时相信，但尚未验证的信息
- 

未知：会影响判断，但目前没有答案的信息
- 
```

如果一个问题包含多个相互独立的决定，AI 应先帮助拆分，再从影响最大或最先阻塞开发的决定开始。

### 阶段二：AI 解释

AI 只解释作出当前判断所需的内容：

- 业务问题和成功标准；
- 相关概念及其区别；
- 当前约束；
- 常见方案分别适合什么条件；
- 每种方案的主要收益、代价和风险。

此时 AI 可以介绍备选方案，但不应直接说“你应该选择某方案”。解释完成后，AI 每次只提出一个关键问题。

阶段完成条件：使用者已经理解“正在决定什么、受什么约束、主要方案有什么差别”。

### 阶段三：使用者判断

使用者不需要写长文，但必须说明理由和代价：

```markdown
我的选择：

选择理由：

依据的事实：
- 

依赖的假设：
- 

我愿意接受的代价：
- 

验证方式：
- 

出现以下情况时重新设计：
- 
```

阶段完成条件：选择、理由、假设、代价和重新设计条件都可以被其他人理解。

### 阶段四：AI 评审

AI 在使用者作出判断后进行评审，不以“是否和 AI 想法相同”作为评价标准。评审结论只能从以下三种选择一种：

- **可落地**：当前证据足以支持实现，风险已有边界和验证方式。
- **补充后落地**：方向可以成立，但必须先补充某项事实、约束或验证。
- **暂不建议落地**：存在高概率破坏业务正确性、安全性或可恢复性的风险。

AI 使用以下格式：

```markdown
评审结论：可落地 / 补充后落地 / 暂不建议落地

判断成立的部分：
- 

关键风险：
- 风险：
  触发条件：
  可能后果：

遗漏的问题：
- 

过度设计检查：
- 当前引入的复杂度是否有已确认需求支撑：
- 可以延后实现的部分：

落地前必须完成：
- 

验证建议：
- 

评审依据中的事实 / 假设 / 未知：
- 
```

阶段完成条件：结论有依据；风险包含触发条件和后果；需要补充或验证的事项可以直接执行。

### 阶段五：留下简短决策记录

评审完成后，将最终结论压缩为本文第 7 节的小型架构决策记录。普通小功能可以只保留对话结论；会影响模块边界、数据所有权、跨模块一致性或公共基础设施的决定，建议保存记录。

## 4. 八维架构思考卡

AI 先选择与当前决策相关的维度，再逐题引导。通常先从业务与边界开始，而不是先讨论技术组件。

### 4.1 业务目标与不变量

要回答：为什么做，以及哪些规则绝不能被破坏。

- 谁遇到了什么问题？
- 成功结果如何观察或验收？
- 这是业务意图、执行过程，还是已经发生的事实？
- 哪条业务规则即使失败、重试或并发发生也必须成立？
- 如果暂时不做，会造成什么真实损失？

完成信号：能用一两句话说明业务价值，并列出至少一个可验证的不变量。

### 4.2 边界与数据所有权

要回答：职责属于哪里，以及谁拥有最终修改权。

- 哪个模块最清楚这条业务规则？
- 哪个模块是这份数据的唯一事实来源？
- 谁可以创建、修改和解释这份数据？
- 其他模块需要的是命令、查询结果，还是领域事实通知？
- 当前方案是否允许一个模块绕过所有者直接修改数据？

完成信号：每份关键数据只有一个明确所有者，跨边界交互方式可以说清楚。

### 4.3 模型与状态

要回答：系统中真正存在什么，以及它如何变化。

- 核心对象表示业务意图、任务、当前快照，还是历史事实？
- 对象的身份和生命周期是什么？
- 哪些状态必须显式存在？
- 哪些操作允许状态迁移，前置条件是什么？
- 是否把多个含义不同的概念塞进了一个万能对象或状态字段？

完成信号：核心对象职责单一，合法与非法状态迁移都可描述。

### 4.4 流程与补偿

要回答：正常情况和失败情况分别怎样结束。

- 正常流程从哪里开始，到什么结果才算完成？
- 哪一步可能部分成功？
- 失败后应该重试、回滚、补偿、转人工，还是保留失败事实？
- 重试是否会重复产生业务结果？
- 用户如何知道操作仍在进行、已经失败或需要处理？

完成信号：除正常流程外，至少能说明最可能发生的异常及处理结果。

### 4.5 数据风险：事务、并发、幂等与一致性

要回答：重复、竞争和部分失败会不会破坏数据。

- 一个业务操作需要同时改变哪些数据？事务边界在哪里？
- 两个请求同时操作同一资源会怎样？
- 相同命令执行两次会不会产生两份结果？
- 跨模块更新失败一半时，系统如何发现并恢复？
- 系统要求强一致，还是允许在明确时间窗口内最终一致？为什么？

完成信号：已经明确事务边界、重复请求结果和并发冲突策略；不需要处理时也能说明原因。

### 4.6 质量属性

要回答：除了“功能能跑”，系统还需要达到什么质量。

- 当前和可预见的数据量、请求量、延迟目标是什么？
- 哪些故障可以降级，哪些必须阻止操作？
- 谁能看、谁能改、谁能审批？是否涉及敏感数据？
- 出错后能否定位到请求、用户、对象和失败步骤？
- 设计能否通过自动化测试验证关键规则？

完成信号：只选择真正影响当前设计的质量属性，并给出可衡量目标或验证方式。

### 4.7 方案权衡与过度设计

要回答：为什么在当前约束下选择这个方案。

- 至少还有一个可行替代方案是什么？
- 当前选择解决了什么，又牺牲了什么？
- 引入的组件、抽象或分布式复杂度由哪项已确认需求支撑？
- 是否可以先用更简单的方案，同时保留清晰演进点？
- 哪些复杂度只是为了尚未确认的未来需求？

完成信号：能用“约束 → 选择 → 理由 → 代价”解释决定，并指出可以延后的部分。

### 4.8 未来演进

要回答：什么变化会使当前决定失效。

- 哪些规模、业务规则或外部依赖变化最可能发生？
- 当前设计把变化隔离在哪里？
- 哪些指标达到阈值时需要重新评估？
- 未来更换实现时，哪些接口或业务事实必须保持稳定？
- 当前是在保留演进边界，还是已经提前实现未经确认的未来？

完成信号：至少写出一个具体、可观察的重新设计触发条件。

## 5. 必须深入检查的触发条件

出现下列情况时，AI 不应停留在基础问题：

| 触发条件 | 必须深入检查 |
| --- | --- |
| 一次操作写入多个资源或模块 | 事务边界、部分失败、一致性、补偿与对账 |
| 请求、回调或消息可能重复 | 幂等键、重复结果、去重保存期限与重放 |
| 多个操作者竞争同一份可变资源 | 并发冲突、不变量、锁或版本策略 |
| 使用异步任务或消息 | 丢失、重复、乱序、积压、失败重试与最终可见性 |
| 依赖外部系统 | 超时、重试边界、降级、熔断、对账与人工恢复 |
| 操作不可逆或影响审计 | 权限、审批、操作记录、撤销或补偿 |
| 涉及敏感数据或租户隔离 | 认证、授权、数据边界、日志脱敏与越权测试 |
| 数据量或耗时可能显著增长 | 容量假设、性能指标、分页/批处理与压力验证 |

## 6. AI 评审重点

AI 评审时优先查找以下问题：

1. **事实不足**：结论是否建立在未经验证的关键假设上？
2. **边界混乱**：是否出现多个模块都能修改同一业务事实？
3. **模型混淆**：是否混淆意图、任务、状态快照和历史事实？
4. **只看正常流程**：失败、重复、并发和人工恢复是否缺失？
5. **技术先行**：是否先决定使用某项技术，再寻找问题证明它有用？
6. **过度设计**：复杂度是否由当前已确认需求支撑？
7. **无法验证**：是否只有抽象目标，没有测试、数据或指标验证方法？
8. **没有演进条件**：是否使用“以后可能”作为理由，却没有重新设计阈值？

评审应指出最重要的少数风险，不以列出问题数量体现专业程度。

## 8. 可复制给其他 AI 的启动提示词

将下面整段发送给 AI，并在最后补充本次功能点：

```text
请使用“架构思考卡”与我讨论一个架构点或功能点。目标是训练我作出架构判断，而不是由你直接替我决定。

请严格遵守以下流程：
1. 一次只讨论一个明确的决定；如果范围太大，先帮助我拆分。
2. 先核对上下文，并把重要信息分成“事实、假设、未知”。没有证据的信息不能当作事实。
3. 先向我解释作出判断所需的业务背景、技术概念、约束和常见方案。可以说明每种方案的适用条件、收益与代价，但在我判断前不要给出推荐答案。
4. 每轮只问我一个当前最关键的问题，让我逐步完成判断。
5. 引导我说明：选择、理由、依据的事实、依赖的假设、接受的代价、验证方式和重新设计触发条件。
6. 只有在我明确完成判断后，才进行架构评审。
7. 评审必须检查业务不变量、模块边界、数据所有权、模型与状态、异常流程、事务、并发、幂等、一致性、性能、安全、可观测性、可测试性、过度设计和未来演进；只展开与当前问题相关的项目。
8. 评审结论只能是“可落地”“补充后落地”或“暂不建议落地”。请说明判断依据、最关键风险、触发条件、可能后果、必须补充的内容和验证建议。
9. 最后把确认结果整理成一份简短架构决策记录。
10. 除非我明确要求，否则不要一次给出完整答案，也不要连续抛出多个问题。

本次功能点：<在这里填写>
相关需求、代码或约束：<可选>
```

## 9. 简短示例：文件导出采用同步还是异步

### 9.1 使用者提出问题

```text
功能点：用户导出查询结果文件。
我现在需要决定：第一版采用同步生成还是异步任务。
```

### 9.2 AI 先整理和解释

```markdown
本轮决策：第一版文件导出的执行方式。

事实：
- 用户会主动发起导出。
- 当前预计单次导出不超过 10,000 条记录。

假设：
- 10,000 条记录能够在现有请求超时以内完成。

未知：
- 同时导出的用户数量。
- 数据量未来的增长速度。

概念解释：
- 同步导出直接在请求内生成并返回文件，链路简单，但处理时间受到请求超时和连接稳定性限制。
- 异步导出先创建任务，再由后台生成文件，适合耗时或数据量不确定的场景，但需要任务状态、重复提交处理、文件保存和清理机制。
- 当前真正需要判断的不是哪项技术更先进，而是现有规模和体验目标是否值得承担异步任务的额外复杂度。

第一个问题：第一版可以接受的最大导出耗时是多少？
```

AI 应根据回答继续一次问一个问题，例如失败后的用户体验、并发数量和可接受的数据上限，而不是立即替使用者选择。

### 9.3 使用者作出判断

```markdown
我的选择：第一版使用同步导出，并限制单次最多 10,000 条。

选择理由：当前数据量有限，同步方案实现和维护成本更低。

依据的事实：
- 当前预计单次导出不超过 10,000 条。

依赖的假设：
- 在目标环境中，10,000 条数据能够稳定在 5 秒内生成。

我愿意接受的代价：
- 超过上限的用户需要缩小查询范围。

验证方式：
- 使用 10,000 条代表性数据执行性能测试，记录 95 分位耗时和内存峰值。

出现以下情况时重新设计：
- 95 分位耗时超过 5 秒；
- 单次导出需求稳定超过 10,000 条；
- 并发导出明显影响正常查询。
```

### 9.4 AI 再评审

```markdown
评审结论：补充后落地

判断成立的部分：
- 当前选择与已知数据规模匹配，没有仅为未来可能性提前引入任务系统。
- 已明确数据上限、性能目标和重新设计触发条件。

关键风险：
- 风险：10,000 条数据在真实字段和文件格式下可能无法满足 5 秒目标。
  触发条件：代表性性能测试的 95 分位耗时超过目标，或内存峰值影响其他请求。
  可能后果：请求超时、进程内存压力和用户重复提交。

遗漏的问题：
- 需要明确用户重复点击导出时是否允许并行执行。

过度设计检查：
- 当前没有引入异步任务系统，复杂度与第一版目标相符。
- 文件长期保存、任务进度和通知机制可以延后。

落地前必须完成：
- 使用代表性数据完成性能验证。
- 明确重复点击的处理规则。

验证建议：
- 测试 1,000、5,000、10,000 条数据下的耗时和内存峰值。
- 验证达到条数上限时返回清晰、可操作的提示。

评审依据中的事实 / 假设 / 未知：
- 10,000 条上限是当前事实；5 秒内完成仍是假设；并发导出数量仍是未知。
```

这个示例中的同步方案只在给定事实和约束下可能成立。如果数据规模、体验目标或资源条件改变，结论也应改变。

## 10. 使用建议

- 小决定只走一轮关键问题和一次评审，不为了完整而填满所有栏目。
- 影响模块边界、数据所有权或一致性的决定，保存第 7 节记录。
- 评审发现关键事实缺失时，先查代码、数据或询问负责人，不用更多假设掩盖未知。
- 实现后用测试和运行结果回看原假设；假设被推翻时更新或替代原决策。
- 衡量成长时，不问“用了多少架构技术”，而问“能否解释选择、代价、证据和改变决定的条件”。
